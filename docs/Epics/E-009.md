# Physically independent Drawing and Atlas composition

## Status and authority
**Owner decisions confirmed through Round 3, implementation not started.** See [[DECISIONS_DRAWING_ATLAS_2026-11-01]]. [[T-051]] remains an API/design gate for remaining concrete contracts, not for re-asking answered product questions.

## Target modules
- **Drawing:** standalone Godot editor/application and independently consumable package **in the same Git repository**. Owns generic layer groups, single-element text layers, raster/objects, tools, snapping, renderers, independent documents/file I/O and transactions. No references to Atlas classes/scenes.
- **Atlas:** consumes Drawing package; registry/bindings for **live linked** vs **independent copied** artwork; maps, **one layer group per floor**, continuous world coordinates, authored-detail selection, entrance navigation, global history and overlays. No second painting implementation.
- **Release target:** desktop is the reference implementation target; Web is under review and is **not yet declared dropped**.

## Critical architecture acceptance
1. A clean Drawing project/package builds and runs without any Atlas source, scenes, autoload or asset data; one canonical library serves both Godot projects in the monorepo.
2. Linked art updates all references; copied art does not. A reused asset can have different Atlas-world placement transforms. Asset deletion, persistence, undo and copy are explicit.
3. Atlas floor identity is a link to a **Drawing layer-group ID**, not a Drawing `Floor` class. Define group/detail tree topology before storing it.
4. Every authored detail of a map uses one world-coordinate reference; raster sampling density can vary. A missing high-detail layer renders **blank**, not an implicit lower-detail underlay or empty full-resolution allocation.
5. At large signed world coordinates, strokes and grid alignment remain stable using an explicitly tested precision strategy (e.g. chunk-local/camera-relative rendering).
6. Atlas undo on a remote map **navigates to the recorded edit origin**; its view navigation must not create new undo commands. Standalone Drawing history is independent.
7. Every text object has one editable text layer; selecting the tool creates nothing; rasterization is explicit/undoable.
8. Painting always owns painting clicks over entrances. Selection/ObjectSelection/Pan double-clicking the same entrance navigates.
9. No historical user-save migration; new Drawing/project formats still have integrity, roundtrip and recovery tests.
10. Web export/release requirements are conditional on an explicit support decision, not silently removed.

## Out of scope
No mandatory native renderer, migration pipeline, two duplicated painter implementations, collaboration/projector feature expansion or giant all-at-once class rewrite. User hands-on Drawing UX acceptance remains required.

## Round 4 — Object editor and Draw workspace
The former “linked artwork” hypothesis was overly broad. The owner's principal reuse case is a reusable **Object Asset** edited through an Object Editor and placed as Atlas **instances**; `Save` edits the source, `Save As` creates an independent copy. Placement transforms are per instance; source artwork and map/floor background drawing remain distinct. [[T-060]] owns assets/instances, [[T-062]] owns the Object Editor. No whole-map live-link facility is implied by these decisions.

Confirmed hierarchy: **Map → Floor group → Detail group → Layers**. Preserve shared world coordinates and blank missing detail (T-061). Global history must restore relevant selection/editing mode and navigate to the originating map (T-054); details of selection-only history and camera remain in T-051.

The proposed uploaded workspace spec is checked in as [[DRAW_MODULE_UI_SPEC]], with implementation under [[T-063]] and feature inventory remaining in [[T-059]]. UI spec is **proposed**, not a claim of owner signoff.

**Additional sequence:** T-060 (asset identity) -> T-062 (Object Editor) -> T-055 (Atlas instances); T-063 (compact Drawing UI) follows the standalone workspace T-053 and can be developed before Atlas integration.

## Round 5 — finalized Save As routing and optional selection undo
- When Object Editor is opened **from Atlas instance A**, `Save As` creates independent Variant B **and automatically rebinds A alone** to B, preserving the original asset and other placed instances. If opened standalone, `Save As` changes no Atlas bindings.
- One global history has an **opt-in selection-change recording setting**, **OFF by default**. Selection-only changes become history entries only when enabled, while undoing ordinary content always restores valid affected selection/editor mode. Selection-only steps never mark artwork dirty.
- T-060/T-062/T-054/T-056 document stable-origin guards, atomic create+rebind, undo/redo of instance binding and opt-in selection-history regression tests. Final handling of an orphaned newly saved file after an undo is still an open safety policy; do not delete it by assumption.

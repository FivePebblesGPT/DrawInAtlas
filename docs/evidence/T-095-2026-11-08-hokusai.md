## Implementation

- Explicit gesture `CAPTURING → DRAINING → COMMITTING` lifecycle, retaining
  frozen source-space samples and paint settings after release; viewport-only
  wheel zoom, middle pan, Pan toolbar and camera setter no longer cancel
  an already released valid stroke.
- A second stroke while draining is blocked with `canvas_error` rather than
  destroying the first stroke. Navigation with the paint button still held
  explicitly cancels for transform correctness. Escape/document/layer/mask
  changes remain deliberate cancellations.
- Optional `NativeHard` class computes swept hard-circle coverage in Rust and
  lets `DrawingEditSession` own selection, clipping, source RGBA8, detached
  preview, atomic history and Undo/Redo.
- Optional `Hokusai` uses four bundled upstream `.myb` presets (hard, soft,
  ink and airbrush) with pin-sized/color controls and fixed pointer pressure.
  Native 64px tiles retain paint across batches; only quantized straight RGBA8
  changed-pixel triples cross the GDExtension boundary. Canonical canvas
  still stages against the original immutable layer pixels; no sparse
  document storage migration.
- Legacy default remains unchanged, Hokusai eraser uses NativeHard, and a
  missing/invalid native extension or preset triggers visible legacy fallback.

## Follow-up checkpoint: prevalidated tile-batch staging (2026-11-08)

**Problem isolated:** instrumented actual Hokusai `.myb` 60px Brush strokes
averaged approximately 115,000 quantized RGB/alpha pixel deltas per stroke.
The `preset_segments` native call and FFI transfer accounted for only about
24–35 ms, while GDScript's `_stage()` path consumed over 1 second in several
runs. Per-pixel `DrawingResult` creation, rollback journal allocations,
source-tile lookup and preview version writes dominated the time. Treat these
as CPU observations, not isolated native raster or real input-to-photon values.

**Change:** `DrawingEditSession.paint_path_hokusai` validates the entire delta
shape and all relative signed coordinates before any edit, applies the frozen
selection/clip, and resolves every touched source tile before mutating the
transaction. This makes per-pixel rollback snapshots unnecessary: a failed
later source lookup or invalid later pixel leaves the already staged preview
unmodified. Valid deltas are composited directly against the *original*
straight-alpha source, never against a previous preview; changed entries in
`_before`/`_after` retain the existing Undo/Redo publication contract. Per
batch, detached preview tile versions are now updated once per dirty storage
tile instead of once per repeated pixel. Storage tile keys remain **signed
64-bit strings** (not `Vector2i`), so large 64-bit anchors do not wrap.

The old pixel-at-a-time staging code was placed **only in a separate copied
standalone stage** as a negative performance control; canonical source kept
the optimized implementation. Both stages used the same Rust binary, 4.8b2
Godot, 1280×900×24 Xvfb, llvmpipe, 512×512 framed document, 786% zoom,
60px Brush, 120 mouse-motion events per stroke (four per Godot frame), five
consecutive strokes, the same canonical fonts/import, and `--audio-driver
Dummy`. Native `preset_segments` stayed unchanged. The control had the same
instrumentation counters as the optimized stage.

| Metric (ms unless noted) | Old staging control p50 / p95 | Batch staging p50 / p95 |
| --- | ---: | ---: |
| Total gesture stage CPU | 1199.565 / 1271.973 | **620.987 / 691.732** |
| Stage batch CPU | 37.092 / 56.994 | **20.423 / 26.211** |
| Input receipt → staged samples | 38.511 / 60.172 | **21.863 / 29.043** |
| Release → commit | 71.330 / 78.758 | 65.896 / 77.348 |
| Frame compositor CPU | 30.871 / 40.211 | 27.945 / 34.931 |
| Texture upload CPU | 0.359 / 1.003 | 0.331 / 0.554 |
| Max queued samples | 4 | 4 |

The p95 stage CPU reduction was approximately **45.6%** on this specific
Xvfb workload; no p95 release-to-commit gain is established. In the optimized
runs the per-stroke native FFI/pigment-export timing was **24.256–26.751 ms**,
while the bulk GDScript staging timing was **530.257–665.794 ms** for
114,892–117,711 changed pixel triples. These timings were measured inside
Godot; they do not cover input-to-photon, Windows, GPU/driver variance or
owner hardware. The same-environment Legacy 60px Brush p95 was **225.456 ms**
CPU stage, and NativeHard p95 **179.721 ms**. Hokusai's 691.732 ms p95 is
still substantially slower, so the owner issue is **not fixed or accepted**.

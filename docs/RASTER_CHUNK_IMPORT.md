# Raster image import and chunk ownership — T-030

## Current Drawing import, tile and storage contract — T-071 (2026-11-02)

**Owner-approved:** [[DECISIONS_DRAWING_ATLAS_2026-11-01]] calls for one canonical Drawing engine, sparse multi-file campaigns, separate authored `DrawingDocument` instances per `(map_id, floor_id, detail_id)`, and explicit pixel density. **Implemented:** `DrawingRasterImport.import_image()` in `addons/drawing/raster_import.gd` imports into a selected raster layer of a generic document at a **signed pixel offset**, with a revision-checked `DrawingEditSession`. It converts a detached source `Image` to straight RGBA8, then applies **bounded edit regions (128 pixels by default)** through a single transaction. On a failed region or unchanged import, the session is cancelled; this is not a sequence of separately saved image chunks. Existing source bytes are not mutated. Exact transparent RGB preservation applies to canonical RGBA8 inputs; other image formats undergo explicit conversion.

**Different sizes mean different things:** (1) `region_edge` defaults to **128** for the temporary import/edit batch; (2) `DrawingDocument.tile_stride` is a **versioned per-document storage geometry**, currently typically 256 for existing documents; (3) GPU upload/display regions are independently selected by rendering code. The old 256-pixel `AtlasRasterChunk` import loop documented below is the **legacy baseline**, not the canonical Drawing import. New tiles are signed sparse straight-RGBA8 (`DrawingRasterTile`), with exact hidden RGB; their immutable physical files are content-addressed compressed `.zst` payloads under `Drawings/chunks/`, **not WebP embedded in the authoritative saved `.scn`**. A generation manifest refers to their hashes, and `AtlasCampaignBundle` atomically promotes a verified root. The portable enclosing campaign also has sibling `Objects/` for reusable sources and `Fonts/` for legally bundled text fonts and licenses; neither is produced by a raw raster import alone. See [storage contract](DRAWING_STORAGE_CONTRACT.md) and the [[T-066]] implementation.

**Measured, not deployed:** [[T-067]] compared storage strides 256, 512, 1024 and 2048 plus physical packing. It recommends **512** for *future new documents* and immutable segmented packs for a future writer, but the deployed v1 writer **still uses individual `.zst` files** and respects the stride of each existing document. Neither benchmark result changes import edit-region size or authorizes automatic retiling. Dense input can produce many populated tiles; blank D-levels create no eager raster allocation. Raster import does not decide Atlas map/floor/detail identity, authored detail navigation or a final GPU update-tile policy.

**Reproduce:** `python3 -m unittest discover -s tests -p 'test_drawing*.py' -v` covers isolated Drawing consumers; `godot --headless --path . --script res://tests/campaign_bundle_smoke.gd` checks saved/reopened signed pixels, sparse chunk hashes and failure recovery. `godot --headless --path . --script res://tests/raster_import_chunks_smoke.gd` specifically checks the **legacy** import algorithm below; do not treat that result alone as proof of the new package's importer. See [storage acceptance examples](DRAWING_STORAGE_CONTRACT.md#reproducible-portability-and-failure-acceptance--t-071).

## Historical T-030 baseline — native `AtlasRasterLayer` import

The description below was correct for the pre-separation `AtlasArtworkEditor` and 256×256 lossless-WebP `.scn` path; those types remain for compatibility/tests, not as the canonical Atlas Drawing import or project save format.

## Source and output

`AtlasArtworkEditor.import_raster(image)` calls `AtlasRasterLayer.from_image_chunks(image)`. The legacy `from_image(image, scale)` method delegates to the same implementation so existing callers remain compatible. The input is a nonempty Godot `Image`; a `null` or empty image, nonfinite `scale`, or nonpositive `scale` is rejected. The returned `AtlasRasterLayer` starts at identity transform with default name/id and stores `pixels_per_unit = scale`; the editor separately assigns its id, authored detail and board-space placement. **The importer itself does not move pixels to the board or search for nontransparent content.**

## What the loop does

The two nested loops visit **rectangular regions** with top-left coordinates `(left, top)` spaced by `AtlasRasterChunk.SIZE` (256). Each iteration calls `Image.get_region(Rect2i(left, top, width, height))`, then constructs an `AtlasRasterChunk` at the corresponding `(left / 256, top / 256)` chunk coordinate and stores it under the matching `"x,y"` key. For an image `W × H`, the result contains `ceil(W/256) × ceil(H/256)` chunks. Partial right/bottom edges use `min(256, remaining pixels)` and are not padded. Image import starts at pixel `(0,0)`, so initial chunk coordinates are nonnegative; the separate `pixel_to_chunk()` helper supports signed board-space chunk addressing with floor division.

`get_region` copies the source rectangle into a temporary `Image`. The `AtlasRasterChunk` constructor then passes it to `canonical_image`, which duplicates the region, decompresses if necessary, removes mipmaps, and converts to `FORMAT_RGBA8`. The chunk retains the **second, independently owned** image and records its actual width/height. For already-RGBA8 input, the chunk's raw base-level RGBA bytes are retained, including RGB values beneath zero alpha; no per-pixel alpha search or handwritten scanning loop occurs. Non-RGBA8 inputs are converted by Godot, so matching the original source **byte-for-byte** is only meaningful for RGBA8 input; source format and data are not mutated. Failed chunk creation aborts the import instead of returning a partially populated layer.

The algorithm visits `O(ceil(W/256) × ceil(H/256))` rectangles and copies/converts an aggregate `O(W×H)` pixels. An individual temporary region and chunk duplicate are at most 256×256 pixels. Chunk memory and native-save encoding are distinct concerns: `AtlasNativeScene` later serializes validated chunks as lossless WebP inside the `.scn` resource graph and verifies exact decoded pixels. The existing separate history/clone paths still make independent decoded image copies. No concrete performance regression was found in this review, so T-030 introduces no speculative caching or wholesale re-encoding.

## Verification

`tests/raster_import_chunks_smoke.gd` checks a 513×257 patterned RGBA8 input (six chunks), byte-exact regions including transparent RGB, one-pixel bottom/right edges, scale/transform metadata, original/derived image independence, RGB8 mipmap normalization, invalid inputs, signed address arithmetic and a native Resource save round trip. Existing layer, dictionary-validation, storage, clipboard, preview and Web/source-pack portability tests continue protecting those boundaries.

# Measure Godot vs native LOD/rendering on huge continuous Atlas maps

**Status: DONE (research decision, 2026-11-03); retain Godot.** No external library has been adopted. **Web is paused / dropped from the active release target as of 2026-11-02.** Reinstatement is a future product decision.

## Separate these systems
- **Canonical editable artwork** belongs to Drawing, in sparse chunks/objects at defined pixel density.
- **Derived display LOD** is mipmaps, tile pyramids, cache streaming and frame-time optimization.
- **Authored detail** is Atlas choosing different content groups at D-levels. An absent high-detail level must be **blank**, not fall through to D0 art.

## Study plan
1. Measure a Godot 4.x baseline with the current raster chunk renderer, viewport culling, camera-relative origin and mipmap/downsampled caches. Include huge positive and negative world coordinates and repeated zoom/pan.
2. Evaluate libvips only as a candidate raster/tile-pyramid producer; random edit invalidation and live texture updates may outweigh preprocessing gains.
3. Evaluate MapLibre Native only if geographic vector-tile semantics actually fit the product. It is **not** a replacement paint engine or automatic authored D-level system.
4. Prefer a narrower native raster backend if it directly reduces Drawing/Atlas complexity; study licensing, distributable binaries, cross-platform compilation and maintainability.
5. **Benchmark desktop first and only.** Web/WASM/GDExtension compatibility is **not** a current acceptance condition. Note foreseeable platform-lock-in, but do not spend implementation time maintaining browser builds unless the owner reactivates Web.
6. Test image fidelity/alpha, blank authored level, edit-to-visible latency, peak RAM/VRAM, frame-time distribution, chunk invalidation, panning at high signed coordinates, package size and engineering complexity.

## Acceptance
Reproducible baseline and candidate results with exact hardware/build, evidence for precision and huge-world positioning, explicit edited-vs-derived-vs-authored LOD separation. Recommend retain Godot, optional acceleration or a backend replacement; **adoption requires a separate ticket**.

## Round 9 — benchmark larger logical chunks independently of renderer
Render/LOD evaluation must not conflate authored-detail switching, derived zoom LOD and raster chunk geometry. Pair representative 256/512/1024/2048 tile datasets with one consistent Godot renderer baseline; compare culling/cache/upload cost, RAM/VRAM, cross-boundary strokes and visible frame-time spikes. Storage size and encode/decode throughput belong to [[T-067]]/[[T-066]], not to speculative native renderer adoption. Larger logical tiles might increase upload churn despite fewer draw calls, so retain smaller comparison results.

## Native rasterizer evaluation separated (2026-11-02)
The owner currently prioritizes **interactive drawing/editing performance** over map-view GPU acceleration. The CPU stroke/compositing backend study is therefore [[T-068]], distinct from this ticket's native/Godot GPU renderer evaluation. Do not declare Blend2D, Skia or any native library adopted until operation-specific benchmarks demonstrate gains after fixing avoidable GDScript full-layer cloning and per-pixel dictionary overhead. This ticket remains relevant to texture update, camera-relative presentation and GPU cache performance.


## 2026-11-03 measured research decision — Done

**Evidence:** [full T-057 report](../DRAWING_LOD_RENDERER_BENCHMARK.md) with pinned Godot 4.8 beta 2, Xvfb/Mesa software-GL/CPU information, reproducible scripts, raw [headless](../benchmarks/T057_2026-11-03_headless.json), [native frame/memory](../benchmarks/T057_2026-11-03_native.json), and [upload](../benchmarks/T057_2026-11-03_upload.json) observations. **No production renderer or persistent-format change** was made by this research ticket.

- Headless `tests/t057_lod_headless.gd` passed **249/249** checks with JSON output (248/248 without the optional file-output assertion). It compared identical sparse two-layer source pixels at storage strides 256, 512, 1024 and 2048, 16 deterministic pans each, bounded 64px display tiles, exact CPU output-cache parity, cache invalidation after an edit, and mean RGBA/alpha error from two 2× derived-downsampling variants. Exact source rendering remained valid around signed seams at 64-bit coordinates beyond ±2⁵³. The cache is a **benchmark-only candidate**, not a shipped feature.
- `tests/t057_lod_native.gd` passed **36/36** actual X11 native checks for a visible D0 pointer stroke, empty authored D1 (no fallback), reversible detail switching, stable ±1,048,576 world units, documented precision loss at 2²⁴ in a single-precision `Vector2` camera, 21 real pan/zoom submission frames, and sampled software renderer/CPU memory monitors. Median/p95 change-to-`frame_post_draw` **14.822/24.558 ms**; not physical input-to-photons or discrete GPU VRAM.
- Repeated `tests/drawing_raster_upload_benchmark.gd` passes all **4** 128/256/512/1024 whole-texture update cases. A full 1024px RGBA8 upload median is 0.318 ms here, separate from texture creation and frame timing. The existing renderer recreates display `ImageTexture` objects on redraw and silently declines over-budget views; a retained, revision-aware GPU tile cache and precision-stable camera require **separate implementation and release-stage tests**.
- Regressions passed on the same pinned engine: T-055 composition **89/89**, T-061 world mapping **125/125**, zoom-LOD contract **29/29**, automatic authored-artwork LOD **27/27**, T-068 renderer benchmark **691/691**, main project import and 83-ticket validator. Deferred large native/legacy CI, Windows physical GPUs and Web remain untested/not required by this desktop research decision.

**Recommendation by workload:** retain Godot for interactive sparse Drawing/Atlas display, prototype an exact revision-aware bounded GPU display-tile cache before adding lossy derived mip levels, and keep authored D-levels distinct. Existing T-068 separately owns edit-to-visible/native CPU performance. libvips (LGPL-2.1-or-later) is an *unbenchmarked optional offline pyramid* candidate, not an adopted dependency; MapLibre Native (BSD-2-Clause) is a mismatch for this app's editable non-geographic source semantics. No code, library, new runtime binary, or maintenance commitment is justified from these screen-only software measurements. The question posed by the research ticket is resolved; actually building the cache or fixing large-camera precision would need its own implementation acceptance.

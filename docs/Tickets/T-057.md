# Measure Godot vs native LOD/rendering on huge continuous Atlas maps

**Status: RESEARCH; no external library chosen.** **Web is paused / dropped from the active release target as of 2026-11-02.** Reinstatement is a future product decision.

## Separate these systems
- **Canonical editable artwork** belongs to Drawing, in sparse chunks/objects at defined pixel density.
- **Derived display LOD** is mipmaps, tile pyramids, cache streaming and frame-time optimization.
- **Authored detail** is Atlas choosing different content groups at D-levels. An absent high-detail level must be **blank**, not fall through to D0 art.

## Study plan
1. Measure a Godot 4.x baseline with the current raster chunk renderer, viewport culling, camera-relative origin and mipmap/downsampled caches. Include huge positive and negative world coordinates and repeated zoom/pan.
2. Evaluate libvips only as a candidate raster/tile-pyramid producer; random edit invalidation and live texture updates may outweigh preprocessing gains.
3. Evaluate MapLibre Native only if geographic vector-tile semantics actually fit the product. It is **not** a replacement paint engine or automatic authored D-level system.
4. Prefer a narrower native raster backend if it directly reduces Drawing/Atlas complexity; study licensing, distributable binaries, cross-platform compilation and maintainability.
5. **Benchmark desktop first and only.** Web/WASM/GDExtension compatibility is **not** a current acceptance condition. Note foreseeable platform-lock-in, but do not spend implementation time maintaining browser builds unless the owner reactivates Web.
6. Test image fidelity/alpha, blank authored level, edit-to-visible latency, peak RAM/VRAM, frame-time distribution, chunk invalidation, panning at high signed coordinates, package size and engineering complexity.

## Acceptance
Reproducible baseline and candidate results with exact hardware/build, evidence for precision and huge-world positioning, explicit edited-vs-derived-vs-authored LOD separation. Recommend retain Godot, optional acceleration or a backend replacement; **adoption requires a separate ticket**.

## Round 9 — benchmark larger logical chunks independently of renderer
Render/LOD evaluation must not conflate authored-detail switching, derived zoom LOD and raster chunk geometry. Pair representative 256/512/1024/2048 tile datasets with one consistent Godot renderer baseline; compare culling/cache/upload cost, RAM/VRAM, cross-boundary strokes and visible frame-time spikes. Storage size and encode/decode throughput belong to [[T-067]]/[[T-066]], not to speculative native renderer adoption. Larger logical tiles might increase upload churn despite fewer draw calls, so retain smaller comparison results.

## Native rasterizer evaluation separated (2026-11-02)
The owner currently prioritizes **interactive drawing/editing performance** over map-view GPU acceleration. The CPU stroke/compositing backend study is therefore [[T-068]], distinct from this ticket's native/Godot GPU renderer evaluation. Do not declare Blend2D, Skia or any native library adopted until operation-specific benchmarks demonstrate gains after fixing avoidable GDScript full-layer cloning and per-pixel dictionary overhead. This ticket remains relevant to texture update, camera-relative presentation and GPU cache performance.

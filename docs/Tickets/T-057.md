# Native map LOD/rendering library feasibility benchmark

**Status: RESEARCH, NOT LIBRARY ADOPTION.** Owner is considering native acceleration.

## Distinguish
- Canonical sparse drawing pixels/objects, editable via Drawing.
- Derived display-resolution mipmaps/pyramids and viewport tile streaming.
- Atlas-authored D-level artwork/surface selection, which cannot be inferred from mipmaps.

## Plan
1. Benchmark current Godot ImageTexture/CanvasItem, mipmap and sparse tile culling baseline with very large signed-coordinate world surfaces.
2. Evaluate libvips for offline/on-demand image tile pyramids (DeepZoom), live-edit invalidation, licensing and library size; it is not inherently a painting engine.
3. Evaluate MapLibre Native only if a vector-tile geographic rendering model is justified; it is not an ordinary bitmap editor.
4. Compare any stronger relevant alternatives; measure panning/zoom frame latency, memory, VRAM budget, alpha, edit-to-display latency, transparent chunk edges, viewport caching, package size and complexity.
5. Test native desktop *and* actual Godot Web build/WASM/GDExtension requirements (where applicable), including threading and hosting headers. Ensure a working non-native fallback if Web export remains a requirement.
6. Propose a bounded backend adapter in Atlas only if measurements justify adoption, with owner approval, license review and rollback path.

## Acceptance
Reproducible benchmark, exact environment/version, source and measured result, crisp authored-vs-derived LOD separation, explicit recommendation to use baseline/optional native/mandatory only with owner acceptance. Library integration is a separate future ticket.

# Decouple Drawing edit operations while retaining coherent undo/history

## Status
**PLANNED / BLOCKED by T-051 and T-052.** History semantics are an explicit owner decision in T-051.

## Problem
`AtlasEditCommand.apply(campaign)`, `AtlasLayerEdit` and `AtlasEditHistory` tie ordinary layer mutations to a campaign graph. A Drawing-only editor must not create a dummy Atlas campaign just to undo a stroke.

## Implementation plan
1. Specify typed Drawing edit intent/result and a target revision or expected-snapshot contract; separate transient previews from persisted mutations.
2. Make drawing operations apply/revert against the Drawing surface, validating selected layer, lock/visibility, detail level and optional mask before committing detached mutations.
3. Add an Atlas command adapter that resolves stable map/floor/surface IDs in `AtlasCampaign` and submits Drawing operations to the existing ordered workspace history. Avoid parallel undo authorities or direct scene-node mutations.
4. Preserve cross-map undo/redo, dirty/savepoint state, cancellation, stale-target rejection, re-render/preview invalidation and immutable before/after snapshots.
5. Measure large-layer snapshot/copy amplification during brush operations; propose chunk-diff optimization only with a benchmark and separate behavior-preserving change.

## Acceptance
- Drawing-only edit history works without `AtlasCampaign`.
- Integrated Atlas history preserves user-visible ordering across map, floor and artwork edits, including undo after navigating to another map.
- A failed/stale edit has no canonical mutation or dirty marker; redo branches and savepoints remain correct.
- Tests verify isolated drawing sessions, mask/lock changes mid-gesture, undo/redo roundtrip and the original atlas history contract.
- No native save schema changes or premature collaboration command protocol.

## Non-goals
Do not implement multiplayer synchronization or combine this with `T-015` legacy conversion.

# Drawing-local history with Atlas global cross-map navigation

**Status: PLANNED.** Owner confirmed **global history** in Atlas and **navigate to originating map A** on undo.

## Plan
1. Define stable Drawing edit transactions recording asset/layer IDs, before/after data or deltas, immutable expected revision and atomic commit/preview/cancel state. Do not require AtlasCampaign.
2. Give the standalone editor a document-local history and dirty/savepoint; Atlas injects a history coordinator/adapter so embedded Drawing cannot also independently record the same edit.
3. Atlas global history commands store **originating map ID, floor-group ID, authored-detail ID and optional camera/edit focus** as well as target Drawing asset ID. This is essential for a live shared asset visible in more than one map.
4. When Ctrl+Z reverses an edit originally made on map A while user views map B, first reverse canonically and navigate/focus A by the approved T-051 rule. Navigation caused by history playback is **not** a new undoable command; guard against re-entrant edits and stale scene IDs.
5. Resolve redo symmetry, deleted-map origins, map/link deletion ordered around artwork changes, and whether a stored camera can still be safely restored. Do not silently ignore invalid target context.
6. Regression coverage: paint shared asset on A/view B -> undo updates both visible references, lands on A; copy asset -> no mutation of original; undo after floor/detail switching; one gesture/one entry; no dirty on rejected edit.
7. Benchmark layer snapshot copying separately; no mandatory optimization or network protocol as part of refactor.

## Acceptance
Drawing-only history requires no Atlas; Atlas has precisely one ordered history; cross-map undo shows origin; shared asset edits are reversed once for all references; navigation never pushes another history entry; stale target is handled deterministically.

## Round 4 — contextual undo/redo, not just data rollback
The owner requests Blender-like history that **affects selection and switches editing modes** while undoing, besides the earlier choice to return to the originating map. Interpret this as required **context restoration**, not as evidence that Blender records every selection action.

### Implementation refinement
- A history step keeps typed **before/after** context: `map_id`, `floor_group_id`, `detail_group_id`, `selected_layer_ids`, `selected_instance_id`, `editor_mode` (surface paint / instance placement / object-source editing), plus stable data target IDs and optional focus/camera anchor.
- Undo reverts the canonical edit and returns to its origin, restores the valid selection and active mode needed to inspect or continue editing; redo applies the edit and restores the corresponding after-context. Do not create an undo entry for history-driven navigation or mode/selection restoration.
- Separate **what changes the document** (must be transactional) from **which UI context history restores** (best-effort validated by stable IDs). Never resurrect an invalid deleted object/instance through UI-only restoration, and never select a same-ID replacement without instance/revision validation.
- Owner decision 2026-11-02: **selection-only changes may be separately undoable if an explicit setting is ON; it is OFF by default.** Mode-only and camera-only actions are not implicitly covered by this toggle. Camera policy and active modal text/stroke playback remain design questions in T-051.
- Add acceptance scenarios: select object X -> move X -> switch to painting on another map -> undo returns to X and placement mode with X selected; source object edit vs instance transform are separate history actions; redo restores destination mode and selection; stale missing selection falls back safely.

## Round 5 — opt-in selection-operation history (owner approved 2026-11-02)

**Config:** `Record selection changes in Undo History`, **default false**. Applies to standalone Drawing's history and to Atlas's one global history via the injected adapter. This setting is separate from mandatory **selection/mode context restoration on content undo**, which always stays enabled.

### Behavior
1. With toggle **OFF**: selecting/deselecting an object, layer or group updates the live selection but **does not add an undo step**. Undo on the next content transaction restores that transaction's relevant selection and editor mode.
2. With toggle **ON**: each *completed, meaningful* selection change records a reversible **selection-only** entry containing before/after stable target IDs and map/floor/detail/editor context. One marquee or multi-select gesture = one step; no-op selections, hover and individual drag samples are not entries.
3. Selection-only steps **do not mutate source artwork, persistent scene content or dirty/savepoint state**. They do participate in the ordered history while recorded. Replaying navigation/selection/mode changes during history playback must not generate new steps.
4. Toggling the setting affects **future** selection commits; it must not rewrite prior history or break redo branches. Proposed implementation: previously recorded selection steps remain until normal history truncation/reset.
5. On missing/stale/deleted targets, the selection replay must fail safely or choose a documented safe fallback; do not bind an ID-reused replacement. Changes in selection-history preference alone must not dirty a project.
6. After Save As through an Atlas Object Instance, the asset creation + instance rebind must be **one logical content transaction**. Undo/redo switches between original/Variant B reference and restores the selected instance and Object Editor/placement mode, regardless of selection-history toggle. Decide separately whether an unreferenced persisted copy remains after undo.

### Regression matrix
- OFF: select A -> select B -> paint -> undo = paint undone (no detour through selection-only events).
- ON: select A -> select B -> undo = A selected, no artwork change or dirty marker; redo = B selected.
- ON: marquee selecting 10 objects creates **one** selection history entry, not ten.
- Toggle ON/OFF with existing history; selection undo then data undo and redo order; navigation caused by replay creates no new entry.
- Object source Save As through A -> new asset+rebind one content entry; undo restores old link and relevant selection/mode even if toggle OFF; independent Save As has no Atlas binding entry.

## Round 6 — intentionally non-destructive Save As history
For Object Editor `Save As` invoked through Atlas instance A, the logical operation creates saved asset B and changes A's source binding. **Undo restores A's prior source reference and selection/editing mode but retains B** as a normal asset in the library; **redo rebinds A to the exact same B ID**. This is intentionally not a full inverse of persistent asset creation. Do not automatically garbage-collect zero-reference variants.

The history/savepoint model must distinguish surviving asset content from the undone binding. If B lives in Atlas project storage, undo need not return the project to its earlier clean savepoint. If B is in a separate asset library, treat its savepoint independently. The specific storage choice is still in T-051. Repeated undo/redo adds no new assets; if B was deliberately deleted while the binding is undone, handle redo as an invalid/stale target rather than inventing a new B.

## Round 7 — precise camera, target failure and settings scope (owner approved)
- On Atlas undo/redo, restore originating map/floor/detail and safe selection/editing mode. If **any of the affected geometry** is currently partially in the viewport, **leave camera translation and zoom unchanged**. Otherwise, **pan only** to bring at least part of the target into view, preserving the **current zoom** (no zoom-to-fit). After a map switch, apply the same visibility test using the destination map's current viewport.
- If the target map/object/selection was deleted or replaced, perform a safe documented fallback with a **visible notification**; do not silently attach to an unrelated same-name object. History must not recurse from mode/selection/camera restoration.
- The `Record selection changes in Undo History` preference is **application-level** and **OFF by default**, for both standalone and Atlas contexts as applicable. It does not turn camera-only/mode-only navigation into content undo steps.
- Object Editor drafts are **not published to sibling linked instances** until Save. Define local draft undo separately from global Atlas published-source transactions; a global published edit may require marking an asset file dirty rather than silently overwriting disk on Ctrl+Z.
- Test partially visible edit => zero camera movement; invisible edit => pan with unchanged zoom; missing target => safe fallback + notification; mode and selection restoration regardless of opt-in selection-history toggle.

## Round 8 — global undo and multiple internal DrawingDocuments
Atlas history must name the **stable `(map_id, floor_id, detail_id, document_id)`** of the affected document. Switching displayed detail/floor changes which document is edited; **in-flight strokes pin their original document ID** until commit/cancel. Undo of a layer move between two documents is one Atlas global transaction that restores both document states and the valid selection/editor context. Lazy-unloaded documents must be safely loaded or replayed through a bounded chunk/delta interface.

Sparse multi-file storage requires explicit **revision/savepoint semantics**: replaying in-memory history is not automatically durable until its modified document manifests and required blobs have been saved. Prior revisions/undo references must not be garbage-collected while reachable. Don't assume a single `.scn` rewrite persists all history-connected artwork. See [[T-066]].

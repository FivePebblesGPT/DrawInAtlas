# Profile and fix slow selection Delete

## Owner finding (2026-11-20)

The owner reports that **deleting the selection** takes a long time, but the exact command is ambiguous: it may mean Delete selected pixels or Deselect/clear-selection. Painting otherwise seems usable. The first profiling task is to identify which action is actually slow before attributing any cost to `clear_rect()`. This is **untimed owner feedback**, not measured latency. Distinguish **Delete selected pixels** (Del/Edit) from **Deselect** (Ctrl+D). The current workspace calls `_delete_selection() → DrawingEditSession.clear_rect(canvas.selected, canvas.selection_mask) → _commit_clipboard_edit()`; the selection bounds need not equal the allowed mask pixels.

## Scope

- Capture both user operations separately (Delete key / Edit > Delete selected pixels, and Ctrl+D / Select > Deselect or blank click), compare their effects, and confirm the owner-reported slow action. Reproduce with 512×512 and sparse/large selections, rectangles, mask islands/holes, empty selections, transparency and signed tile boundaries. Record OS/GPU/Godot/build SHA, zoom, touched tiles, input and time.
- Attribute command-to-visible completion, mask evaluation, tile work, GDExtension/Rust updates (if reached), commit/Undo journal, preview/texture upload, long frames and bytes. Report repeated cold/warm p50/p95 before/after.
- Apply **one profile-led improvement** without blindly clearing huge bounding rectangles or bypassing Rust-owned authority. Record counterfactuals and any regressions.
- Distinguish ordinary content deletion from selection-only non-dirty deselection. Preserve safe cancellation and pending edit restrictions.

## Implementation and evidence — 2026-11-22

**Diagnosis:** the Delete command, not Deselect, was slow on a 512×512 sparse selection with eight stored pixels. `clear_rect()` inherited `fill_rect()`'s full-area per-pixel staging, spending ~1.13 seconds just visiting empty positions. The ordinary content commit took <1.2 ms; clearing the selection channel itself took microseconds. This was established using identical baseline and optimized Godot model and native-X11 fixtures.

**Fix:** `DrawingEditSession.clear_rect()` now uses the document's occupied/lazy tile-key index, screens out nonintersecting tiles, resolves only eligible source tiles, and stages exact nonzero RGBA8 source pixels that pass the selection mask. A second pass clears unpublished staged changes in mixed sessions. The candidate limit bounds actual occupied work, while 131,072² sparse selection bounds do not cause dense iteration or oversized allocations. Existing failure handling restores the detached edit preview, including corrupt lazy sources and candidate-budget exhaustion. Shared Drawing code serves Atlas without a second raster authority or new Legacy path.

**Measured native display:** matched 7-sample `Delete` key to two render frames and framebuffer-read completion on 1010×720, 400% zoom, Godot 4.8 beta3 + X11/Xvfb. Delete p50 **1,212.5 ms → 21.3 ms** (about 57×), p95 **1,281.1 ms → 22.6 ms**. Repeated after-fix run: Delete p50 24.2 ms, p95 30.6 ms. Ctrl+D baseline p50 14.4 ms; after p50 15.5 ms; no dirty document or changed image. No physical hardware/scanout claim.

**Acceptance evidence:** [T-221 measured diagnosis, headless and native/Atlas results](../evidence/T-221-2026-11-22-selection-delete.md), `drawing/tests/t221_selection_delete_{benchmark,regression,native}.gd` and `tests/t221_atlas_selection_delete.gd`. New model 62/62, native X11 25/25, Atlas native history/persistence 19/19, plus existing T-088/T-096/T-130/T-148/T-055 regression suites. Standalone `.drawing` and Atlas generation Save/Open preserve byte-for-byte hidden RGB and undo/redo; separately measured Ctrl+D is non-dirty. The harness also records source SHA-256 before/after native Delete. Ticket-store validation passes.

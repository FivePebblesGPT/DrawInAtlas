# Provide a Web-compatible player-output fallback

## Source
[[Archive/2026-10-30/IMPLEMENTATION_PLAN#Current execution milestones (1–8)|Execution milestone 7]]: Web fallback.

## Acceptance
- Define a presentation fallback when native multi-window/projector features are unavailable.
- Preserve the same player projection/privacy contract without mandatory native-only APIs in the core.
- Keep Web export compatible and distinguish build checks from browser runtime evidence.
- Browser smoke remains explicitly deferred until the user authorizes changing that priority; agree runtime acceptance when scheduling this ticket.

## Engineering checkpoint (2026-11-01)

- Added `AtlasPlayerOutputSession.open_embedded(host)` for a dedicated,
  texture-only single-window fallback without native projector windows. It
  shares T-039's sanitized capture inputs and T-040's private GPU capture and
  revalidates the input fingerprint on completion. Empty hosts only; opaque
  input-blocking black backing; no GM nodes or source campaign in output.
- Captures are blank before explicit authorization and fail closed on invalid
  grants, host resize/hide, incompatible framing, renderer failure, revocation
  and stale async readback. Follow/freeze, output closing and session removal
  are covered. Superseded captures cannot revoke newer images.
- Tests: `player_web_fallback_smoke.gd` (headless) and
  `player_web_fallback_visual.gd` (native framebuffer), included in CI.
  Full behavior and limitations: `docs/PLAYER_OUTPUT_WORKFLOW.md`.
- **Still open:** no production trusted publication controller or GM/player
  view switching, no automatic permission-change subscription, browser runtime
  deferred per ticket, and no physical or owner usability acceptance. A Web
  export build is not evidence of browser runtime compatibility.

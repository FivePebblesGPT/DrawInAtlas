# Reject Bucket release after same-ID map/floor/campaign replacement

**Parent:** [T-023](T-023.md). **State:** Done for this narrow, independent
transaction-authorization fix. The parent remains Ready for explicit approval
of the Bucket fill/preview interaction policy; this ticket does not inherit
or bypass that owner decision.

## Defect

The pending Bucket preview already snapshots its selected layer's serialized
pixel/metadata dictionary, source IDs, and exact edit mask. A reconstructed
map or floor Resource can reuse **all** of those values. If it replaces the
original in the campaign while the pointer is held, release may still publish
the detached candidate onto a different graph and append an Undo command.
Swapping the campaign owner or detaching the original map/floor from its
registry has the same authorization ambiguity.

## Scoped fix

- Capture the **actual** campaign, map and floor Resource references when a
  valid preview is created. Keep the existing ID, raster snapshot and edit-mask
  comparisons; all must agree on release.
- Require the campaign's registered map and the map's registered floor to be
  the same live Resources. A same-ID replacement or detached original must
  reject, even when raster bytes and metadata are otherwise identical.
- Clear captured references on cancel, invalid release, and successful
  publication. A subsequent fresh gesture still publishes and Undo/Redoes one
  complete raster transaction. No serialized schema or fill policy changes.
- Preserve legitimate edits to unrelated layers and the existing raster
  source-data equality boundary; do not impose identity on history-replaced
  layer objects, which may change during an unrelated edit.

# Remove appearance-only UI test assertions; require visual inspection instead

## Problem

T-251/T-260 automated geometry checks canonized an unattractive dock-toggle
placement that remained visibly wrong in actual Drawing screenshots. The
ColorPicker likewise passed native checks despite unnecessary whitespace.
Checking layout rectangles or captured-screenshot counts does **not** establish
visual design correctness. It can accidentally freeze the broken layout into
a supposedly successful test contract.

Follow the root [AGENTS.md](../../AGENTS.md) visual workflow: render the actual
application, **look at the screenshots**, compare to the owner's originals,
correct the UI, and only then validate functional invariants. This ticket is
test-suite cleanup, **not** implementation of the underlying UI corrections
and **not** T-250 owner signoff.

## Scope and acceptance

- [x] Audit the current Drawing and Atlas UI-focused Godot suites, Python
      contract assertions and associated CI workflows. Record each
      appearance-only assertion with file/line, its purpose and disposition.
      Start with T-251/T-260 toggle width/gutter/origin tests and nearby dock,
      ColorPicker, panel and floating-host geometry checks; do not assume
      whole files are expendable.
- [x] Remove or refactor assertions whose **sole** purpose is to declare
      visual correctness (pixel positions, decorative widths/margins, spacing,
      aesthetic alignment, screenshot-existence-as-proof or arrow appearance)
      without verifying state, a state transition, input behavior or latency.
      Do not replace them with equivalent cosmetic assertions or image hashes
      whose only purpose is subjective UI acceptance.
- [x] Preserve—and improve when necessary—tests for model state, actual
      pointer/keyboard transitions, click-target reachability/interception,
      focus, context menus, cancellation/rollback, accessibility behavior,
      persistence, pixel correctness, error paths, history and performance.
      Geometry is permissible when it is **causally necessary** for one of
      these functional contracts; prefer end-to-end event tests over arbitrary
      coordinate constants. Split mixed tests rather than deleting their
      meaningful checks.
- [ ] Keep optional *real application* screenshots for human visual review,
      but stop counting generated screenshot files or passing bounds checks as
      visual approval. Document the screenshots **actually opened and inspected**
      across relevant dock states, panel widths and scales. Keep T-250's
      independent owner review open until explicitly approved.
- [ ] Reconcile affected check counts, CI log verifiers, documentation and
      evidence with the surviving behavioral suites; ensure clean-running
      standalone Drawing and embedded Atlas paths. Do not alter historical
      evidence to pretend a removed appearance assertion never existed.
- [ ] Verify `python3 tools/validate_ticket_store.py` and the relevant
      CI/test-contract suites; report exactly what was removed, what
      functional tests remain and any genuine regressions.

## Boundaries

No application layout fixes in this ticket; those need their own measured and
visually inspected corrective tasks. Do not weaken native raster/history
safety, state transitions, performance thresholds or accessibility contracts.
Do not mark any owner-facing UX ticket Done merely because cosmetic assertions
were removed. Ticket may be completed autonomously once the cleanup and
functional validation are evidenced; owner T-250 remains Manual Review.

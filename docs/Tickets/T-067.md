# Benchmark larger raster chunk geometry and physical storage packing

**Status: COMPLETED — deterministic benchmarks and a bounded recommendation (2026-11-02).** Larger chunks are desired for lower sparse-file and metadata overhead and better potential compression. Exact winning size is not yet measured. T-066 has since delivered a per-document versioned `v1` sparse schema; T-067 supplies the geometry/packing evidence **without silently changing already saved 256-stride documents or claiming a pack writer exists**.

## Controlled variants
- Logical tile dimensions: **256 (current baseline), 512, 1024 (initial engineering hypothesis), 2048** square pixels. A full decoded RGBA8 chunk is 0.25, 1, 4 and 16 MiB respectively; verify memory/undo budget assumptions with actual Godot buffers.
- Independently vary **physical layout**: one encoded chunk/file; per-document pack or shard; shared content-addressed blob store with an index. Do not infer one chunk = one operating-system file.
- Use exact same image content and codec settings for geometry comparisons. The existing code's `AtlasRasterChunk.SIZE = 256`, SHA-256 content identity and validated `AtlasWebPStore` are the **reference implementation**, not proof 256 is optimal.

## Representative workloads
1. Several continuous dense layers covering a sizable region; gradients/painted scenes and long strokes crossing chunks.
2. Tiny isolated strokes/marks spread across very distant positive and negative world positions (measure **sparse inflation**: nonempty area vs allocated/encoded tile extents).
3. Imported texture-like or high-entropy images, alpha/hidden RGB correctness, partial edge chunks, and multiple layer densities.
4. Zoom/pan and painting across chunk seams with different cache budgets; repeated one-pixel changes and grouped brush gestures.
5. One small save on a huge sparse multi-document campaign, warm/cold reopen, chunk decode/cache eviction and repeat undo/redo with meaningful history depth.
6. Interruption/failure injection on staged payloads, manifests and generation-pointer publication under candidate packing schemes.

## Measurements / output
- Chart encoded size, total project bytes **including directory/metadata**, number of logical chunks, number of physical files and storage index bytes, per workload and variant.
- Median/p95 edit-to-render and edit-to-committed-save latency; encode/decode throughput, read/write calls, viewport frame spikes, undo delta/snapshot memory, peak RAM/VRAM and cache churn.
- Correctness checks: exact decoded pixel bytes (including RGBA hidden RGB), continuous seams, density conversion, negative signed chunk coordinates, offset math and post-crash recovery.
- Record OS/filesystem and CPU/RAM/storage; test native Windows/Linux representative machines if available. Flag any codec/texture size limits explicitly.
- Summarize **recommended production tile size and pack strategy**, plus conditions to choose a different result for high-density continuous art versus scattered small marks. Resist adding uncontrolled per-chunk adaptive dimensions unless necessary.

## Acceptance
A reproducible benchmark with inputs/scripts, measurement tables and a concrete size/packing recommendation for T-052/T-066. Versioned **per-document tile-size** invariant and explicit retiling strategy are designed before saving first production format. Larger chunks need to reduce real overhead **without unacceptable edit latency, cache pressure or undo memory cost**. No automatic assumption that 1024 always wins.

## Relation
[[T-066]] owns file format and crash-safe multi-file writes. [[T-052]] owns Drawing's generic raster/chunk model. [[T-057]] owns renderer/derived LOD measurement. No old-user-save migration is required; no Web compatibility gate.

## Coordinate T-068 independent edit tiles
The logical **compressed storage tile size** (T-067) and the optimal **in-memory edit/delta/GPU update region** (T-068) may differ. Benchmark them independently. Larger compressed tiles must not require full decoded-tile duplication per 4px brush stroke if region copy-on-write/delta tracking is sufficient. Measure tile-size effect on end-to-end editing while keeping native painter comparisons controlled.


## Completed benchmark and verification evidence (2026-11-02)

- **Full methods, measurements, limits and recommendation:** [Drawing chunk geometry report](../DRAWING_CHUNK_GEOMETRY_BENCHMARK.md). Raw output: [48 layout cases / CSV](../benchmarks/T067_2026-11-02_layouts.csv), [16 workloads / JSON](../benchmarks/T067_2026-11-02_layouts.json), [Godot editor/save measurements](../benchmarks/T067_2026-11-02_native.json) and [Mesa software-GL upload measurements](../benchmarks/T067_2026-11-02_upload.json).
- Executed `python3 tools/benchmarks/chunk_geometry.py --output /mnt/data/t067-evidence --repeats 3` over all **four** strides, **four** representative workloads and **three** physical layouts: **48 physically written and byte-verified layouts**. Synthetic inputs use fixed seed 670021 and real native Zstandard level-3 frames; 512/1024/2048 do not inherit any 256-only chunk assumption. CPU/OS/filesystem captured in the report.
- `python3 -m unittest discover -s tests -p test_chunk_geometry.py -v`: **6 passed**, including exact hidden transparent RGB, signed >2⁵³ positions, density-partition independence, partial edges, packed-index readback, bounded caches and staged-pointer failure simulation. Godot's own Zstd decoder decoded the Python/C Zstd fixture, and the C Zstd decoder decoded a Godot-created fixture.
- `godot --headless --path . --script res://tests/chunk_geometry_benchmark.gd`: **386 checks**, no failures; 13 signed x/y seam-crossing brushes per stride, local undo/redo, camera-anchored rendering, canonical alpha-zero RGB, 3 actual `AtlasCampaignBundle` save/reopen generations per stride. Process peak RSS was collected with separate `/usr/bin/time -v` runs; 2048 saved a 1px edit in ~301 ms median vs ~26 ms at 512 on this Linux host.
- `xvfb-run ... res://tests/chunk_geometry_upload_benchmark.gd`: **four software-GL tile sizes passed**; full `ImageTexture.update` medians increase from 0.02 ms at 256 to 0.97 ms at 2048. These are Mesa llvmpipe observations, **not discrete GPU VRAM benchmarks**.
- Read-only display tests, T-066's real generation recovery and stale-writer tests, and the independent standalone Drawing packaging regressions remain authoritative; this spike does **not** substitute a production pack publisher or revalidate every native Windows GPU combination.
- **Recommendation:** target **512×512** as the future new-document default; retain per-document saved stride; offer 256 for isolated sparse marks and 1024 only after explicit dense-art profiling. **Reject 2048 as the general default** due to inflated decoded working set and synchronous edit/save amplification. Prefer **immutable content-addressed segmented shared packs with a versioned checked index** as the physical next step, while **retaining T-066's tested one-file-per-blob v1** until pack staging, verification, recovery and Windows tests exist. No production default, existing document, or save format was silently modified by this research ticket.
- **Retiling plan:** stable global signed coordinates and canonical RGBA8 including hidden RGB, explicit floor-division repartition, original document/layer IDs and density retained, unallocated zero tiles, immutable staged replacement generation, atomic root switch and old-generation recovery. Details and preconditions are in the linked report. No automatic migration of old `.scn` saves.

**Closure note:** T-067 is research acceptance (measurement and recommendation) rather than implementing pack-v2, a production default switch, renderer LOD, or a native painting backend. T-057/T-068 own the latter evaluations; T-066 follow-up work must implement any changed physical save format. This ticket has no owner-review gate and does not close T-056 or T-059.

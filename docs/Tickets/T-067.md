# Benchmark larger raster chunk geometry and physical storage packing

**Status: PLANNED — owner rejected 256×256 as a hard-coded new target (2026-11-02).** Larger chunks are desired for lower sparse-file and metadata overhead and better potential compression. Exact winning size is not yet measured. Complete this spike **before T-066 freezes the new file schema and T-052 hard-codes new chunk geometry**.

## Controlled variants
- Logical tile dimensions: **256 (current baseline), 512, 1024 (initial engineering hypothesis), 2048** square pixels. A full decoded RGBA8 chunk is 0.25, 1, 4 and 16 MiB respectively; verify memory/undo budget assumptions with actual Godot buffers.
- Independently vary **physical layout**: one encoded chunk/file; per-document pack or shard; shared content-addressed blob store with an index. Do not infer one chunk = one operating-system file.
- Use exact same image content and codec settings for geometry comparisons. The existing code's `AtlasRasterChunk.SIZE = 256`, SHA-256 content identity and validated `AtlasWebPStore` are the **reference implementation**, not proof 256 is optimal.

## Representative workloads
1. Several continuous dense layers covering a sizable region; gradients/painted scenes and long strokes crossing chunks.
2. Tiny isolated strokes/marks spread across very distant positive and negative world positions (measure **sparse inflation**: nonempty area vs allocated/encoded tile extents).
3. Imported texture-like or high-entropy images, alpha/hidden RGB correctness, partial edge chunks, and multiple layer densities.
4. Zoom/pan and painting across chunk seams with different cache budgets; repeated one-pixel changes and grouped brush gestures.
5. One small save on a huge sparse multi-document campaign, warm/cold reopen, chunk decode/cache eviction and repeat undo/redo with meaningful history depth.
6. Interruption/failure injection on staged payloads, manifests and generation-pointer publication under candidate packing schemes.

## Measurements / output
- Chart encoded size, total project bytes **including directory/metadata**, number of logical chunks, number of physical files and storage index bytes, per workload and variant.
- Median/p95 edit-to-render and edit-to-committed-save latency; encode/decode throughput, read/write calls, viewport frame spikes, undo delta/snapshot memory, peak RAM/VRAM and cache churn.
- Correctness checks: exact decoded pixel bytes (including RGBA hidden RGB), continuous seams, density conversion, negative signed chunk coordinates, offset math and post-crash recovery.
- Record OS/filesystem and CPU/RAM/storage; test native Windows/Linux representative machines if available. Flag any codec/texture size limits explicitly.
- Summarize **recommended production tile size and pack strategy**, plus conditions to choose a different result for high-density continuous art versus scattered small marks. Resist adding uncontrolled per-chunk adaptive dimensions unless necessary.

## Acceptance
A reproducible benchmark with inputs/scripts, measurement tables and a concrete size/packing recommendation for T-052/T-066. Versioned **per-document tile-size** invariant and explicit retiling strategy are designed before saving first production format. Larger chunks need to reduce real overhead **without unacceptable edit latency, cache pressure or undo memory cost**. No automatic assumption that 1024 always wins.

## Relation
[[T-066]] owns file format and crash-safe multi-file writes. [[T-052]] owns Drawing's generic raster/chunk model. [[T-057]] owns renderer/derived LOD measurement. No old-user-save migration is required; no Web compatibility gate.

The logical **compressed storage tile size** (T-067) and the optimal **in-memory edit/delta/GPU update region** (T-068) may differ. Benchmark them independently. Larger compressed tiles must not require full decoded-tile duplication per 4px brush stroke if region copy-on-write/delta tracking is sufficient. Measure tile-size effect on end-to-end editing while keeping native painter comparisons controlled.

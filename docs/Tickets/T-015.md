# Retire the battlemat placement model without losing artwork

## Source
[[ManualReview_2026-10-30#Usability testing|Usability testing]], item 11. The user's later revision in [[E-006]] retires battlemats entirely, rather than adding only a nesting restriction.

## Acceptance
- Inventory old battlemap/footprint ownership, nesting, commands and persistence dependencies.
- Define an explicit preservation/conversion policy for existing artwork, coordinates, units, layers and references; obtain approval before changing stored data.
- Remove obsolete battlemat-specific ownership/creation paths according to [[T-012]].
- Keep genuine unrelated relationships only when their purpose is explicitly justified; do not flatten all relationships blindly.
- Revalidate editing/history/native saving after the approved cleanup.

## Investigation and compatibility guard — 2026-10-30 (approval pending)

- Inventoried the current map/floor/layer registry, legacy `BATTLEMAP` kind, optional `AtlasPlacement` footprints, directed `AtlasMapLink` graph, shared/orphaned/symbolic placements, link/creation undo, registered reference captures, navigation/backlinks, and validated native `.scn` persistence. Full dependency and coordinate analysis: [[LEGACY_PLACEMENT_MIGRATION]]. This supersedes the older assumption that a map or battlemap label alone proves the document should be flattened.
- Added **read-only** `AtlasLegacyMigrationAudit.inspect(campaign)`: deterministic per-map/floor/layer/link/placement metadata inventory with explicit risks and a candidate spatial transform, always marked `approval_required`. No user data or raster pixels are modified or exported by the inspector.
- Added `tests/legacy_migration_audit_smoke.gd`, covering stored legacy kinds, shared/symbolic/orphaned/conflicting/missing placements, signed raster chunks and alpha, independent terrain geometry, repeatable nonmutating audits and isolated native-save roundtrip; added a CI step.
- **Not accepted/closed:** the proposed policy (copy-first, individually selected spatial conversions, retention of ambiguous/symbolic maps as independent, explicit original-retirement approval, lossless conversion or refusal) needs the user's explicit approval **before writing a migrated save**. No destructive cleanup, schema change, stored-data conversion or checkbox change has occurred. Subsequent conversion would require lossless ink/raster/terrain/units implementation, transactional rollback and full editing/history/native-export gates.

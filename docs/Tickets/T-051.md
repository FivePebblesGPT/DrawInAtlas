# Finalize Drawing/Atlas document, file and asset-transaction contracts

**Status: MOST OWNER CHOICES RESOLVED; core DrawingDocument granularity still OPEN.** Latest binding choices are in Round 7 below; earlier "Remaining" sections are historic and superseded where explicitly answered.  See [[DECISIONS_DRAWING_ATLAS_2026-11-01]]. Do not ask again whether the repos must be separate, whether floors are layer groups, whether missing detail is blank, or whether global undo navigates; those are answered.

## Confirmed
- One **monorepo**, two independently runnable Godot projects; Drawing is a reusable package with a single implementation.
- Drawings can live outside Atlas; Atlas supports shared **linked** and independent **copied** artwork.
- One Atlas floor maps to a Drawing layer group; Drawing has no floor domain concept.
- Atlas controls world surfaces and authored LOD. All map detail levels use continuous shared world coordinates; absent high-detail artwork is **blank**, with no implicit lower-detail underlay.
- Drawing owns snap functionality; text is one editable element per layer created on first successful edit and later rasterized.
- Atlas global undo navigates to the origin map. Paint clicks paint; Selection/ObjectSelection/Pan double-click same entrance to navigate.
- No old user-save migrations. Web **may** be dropped, not confirmed dropped.

## Remaining owner/API decisions — narrow scope
1. Is reusable **Object Asset** linking initially within Atlas's registry only, or can the Object Editor source be an external live file? What happens on external edits, asset removal and duplicate references?
2. Given the fixed **Map → Floor group → Detail group → Layers** hierarchy, do authored details share one DrawingDocument with nested groups, or are distinct DrawingDocuments presented through one Atlas hierarchy? Can different Atlas floors show a common Drawing layer without moving it?
3. What canonical world-unit and resolution policy applies at each detail level? Specify asset-local -> Atlas-world transform, rotation/scale allowed, and layer transforms. Prove integer/chunk/local precision at distant signed positions (see T-061).
4. The owner wants Blender-like selection and mode restoration. Specify which selection-only/mode-only operations become undoable entries, exact camera behavior, how to recover a deleted target and whether redo restores its after-context.
5. Empty-detail UI: are grid/entrance overlays visible when raster artwork is blank, and which control returns to D0? Do not render D0 artwork as backdrop.
6. Is Web an actual product/release target? If dropped, record explicit scope change in E-007/T-044/export checks; otherwise native fallback may be required.
7. File format choice for standalone Drawing, reusable Object Assets and Atlas projects, including stable source/instance references and recovery. No migration constraints.
8. Text font bundling/fallback, entrance double-click threshold/overlap choice and first minimal feature inventory (T-059).
9. Monorepo **physical layout** compatible with the existing Atlas-root `project.godot`: one canonical Drawing source tree, packaging/version contract, independent clean builds without accidental nested Godot import/global `class_name` collisions.

## Round 4 answer and narrowed open decisions
**Confirmed:** The user's linked-artwork concept is a reusable Object Asset authored in an Object Editor and placed via linked instances in Atlas, **not** primarily linking entire map documents. Source `Save` updates all linked instances; `Save As` creates a separate asset. Confirmed group order: **Map → Floor group → Detail group → Layers**. Undo should navigate to the originating context and affect selection/editing mode, Blender-style, as specified within our own history system. See [[T-060]], [[T-062]], [[T-054]].

**Still need explicit decisions:**
1. **RESOLVED (2026-11-02):** `Save As` after entering the Object Editor through an Atlas instance **creates a new independent asset and automatically rebinds only that originating instance** to it; other instances retain the old source. Standalone/independent editor `Save As` creates a new asset without rebinding an instance. Decide only the atomic transaction / saved-copy undo lifecycle, not the product behavior.
2. Is the Object Editor a distinct workspace/mode within Drawing, a specialized tab in Atlas using Drawing, or both? Does a reusable object support multiple Drawing layers/groups and nested asset instances?
3. Are placing/transforming instances and editing their source separate modes with obvious UI/keyboard cues? Should source edits propagate on every edit or only on `Save`? What if two editors have the same source open?
4. **RESOLVED for selection-only (2026-11-02):** provide **Record selection changes in Undo History**, default **OFF**. When ON, meaningful committed selection changes add history entries; when OFF they don't. Either way, content edits restore the relevant selection/editing mode. Mode-only and camera-only steps remain out of scope unless separately approved; redo/deleted-target policies need finalization.
5. Which camera location/zoom is restored when history jumps to the edit-origin map?
6. Confirm or revise the uploaded **proposed** [[DRAW_MODULE_UI_SPEC]] and its BarDivider/overflow behavior; it does not replace the promised tool feature inventory.

## Round 5 — new implementation contract gates
- Object Editor opened from a placed castle captures the **originating instance ID, source asset ID, map/floor/detail and revision**. Save As clones to Variant B and rebinds **that instance only**, leaving sibling instances and the original asset untouched. Undo/redo restores binding and relevant context. Independent Save As has no Atlas rebind side effect.
- A history setting **Record selection changes in Undo History**, **OFF by default**, is required. Implement via Drawing's generic history service and Atlas global history adapter. Capture one history entry per completed selection action only when enabled; never record no-op/replay selections or dirty a document from a selection-only entry. Existing content commands still restore selection and mode regardless of the toggle.
- **RESOLVED (2026-11-02):** undoing Save As restores the instance's original binding but **retains the newly saved Variant B** in the asset library; redo reuses the same B ID. User-initiated deletion is separate. **Still open:** asset-library ownership/savepoint dirty semantics, source-edit conflicts, modal/draft preservation on stale origin, and whether selection-history preference is per-workspace or persisted across sessions. Default OFF is approved; preference storage scope is not.

## Round 6 retention rule
The owner approved **retaining unreferenced saved Object Assets after undo**. T-051 no longer needs an answer about deleting B. The API/storage contract must specify where retained assets live, how they appear in the library, and how a project savepoint reports the surviving new asset. Deleting B is an explicit separate user operation, never an automatic side effect of undo.

## Round 7 — owner answers recorded 2026-11-02

**Settled product policies (do not ask again):**
- `Campaign.scn` (or its eventual accepted file format) and sibling **`Objects/`** travel together, referenced by relative paths and stable Object IDs.
- Publish Object Editor changes to linked instances **only on Save**; draft changes stay private. Separate Object Editor document tab using Drawing, with Asset Browser dock.
- Authored D-levels have independent explicit pixel densities with default progression, all in common world coordinates.
- History returns to origin map/mode/selection; **leave camera unchanged if edited content is partly visible**, otherwise pan to reveal at **unchanged zoom**. Missing target => safe fallback + notification.
- Windows/Linux desktop active; **Web dropped for now**, T-044 archived under [[Archive/Web/T-044]]. App-level `Record selection changes` preference, default OFF.
- Blank D-level shows grid and entrance/navigation overlays but no lower-level artwork.
- Object Assets **may contain child Object Assets**; prevent cycles and handle dependency loading safely (T-064). Initial instance overrides: only transform and visibility.
- Deleting an Object Asset prompts to remove placements, retain inspectable `NULL` placeholders, or cancel.
- Known required fonts bundled in portable project save with stable font references (licensing and exact storage layout in implementation).
- Entrance double-click time/distance configurable with stable-ID hit testing.
- Previous Save As rule remains: entered through instance A -> create new B and rebind A only; undo leaves B saved; redo reuses B.

### Only truly blocking decisions to refine
1. **DrawingDocument ownership granularity.** The *logical* hierarchy is fixed (`Map → Floor group → Detail group → Layers`) but should the physical DrawingDocument be **A** one per map with nested groups, **B** one per floor/detail, or **C** one per floor? Recommendation A; still unapproved. Test independent Drawing open/edit of a full map vs one detail, memory and bulk layer operations.
2. **Persistence transaction boundary.** File schema and rename/move/save mechanics for `Campaign file + Objects/`: project-relative asset identity, atomic rename/write/rollback for a new variant+binding, recovery if the campaign file and object file save out of sync. `Save` publishes when pressed, not during brush gestures; define how undo of a published source save affects disk and dirty state.
3. **Nested dependency semantics.** Object Asset child references, direct/indirect cycle rejection, Save As parent copy semantics (copy references or clone children), update propagation, stale/missing child refs and maximum validated nesting complexity. T-064 is designed to isolate this.
4. **Atlas object-instance visibility in authored details.** At a blank D1, the **navigation overlays remain**. Do object instances live only in the selected detail group, persist across details, or optionally have a global overlay? Decide without violating blank authored-artwork promise.

### Engineering choices that need no immediate owner intervention
Godot two-project monorepo layout without duplicate source/class name conflicts; safe missing-asset placeholder renderer; robust app setting persistence; font bundling format/licence; configurable double-click default values. Record as implementation choices and verify tests.

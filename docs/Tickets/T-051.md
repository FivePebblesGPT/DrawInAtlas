# Finalize remaining Drawing / Atlas contracts (Option B approved)

**Status: DONE (2026-11-02) — testable contract and isolated third-consumer build delivered; engine extraction and production storage remain future tickets.** The consolidated owner decision record is [[DECISIONS_DRAWING_ATLAS_2026-11-01]]. Do not reopen its confirmed choices without demonstrating a conflict.

## Approved architectural choices
- One repository, independent runnable Drawing Godot project and reusable single Drawing package, with no dependency on Atlas from Drawing.
- The Atlas user sees **Map → Floor group → Detail group → Layers**.
- **Option B selected:** one **generic internal DrawingDocument per map/floor/detail combination**; Atlas resolves its identity, lifetime and presentation. Drawing does not contain a Floor/AtlasDetail domain type. The per-detail document is **not** a required separately openable user file or tab.
- The standalone Drawing program **still exists** and supports independent ordinary drawings; object-source editing uses the same engine in a dedicated document tab.
- World coordinates shared for a map; per-detail explicit raster pixel densities; sparse signed chunks and **sparse multi-file persisted artwork**.
- Portable project includes native campaign file, sibling **`Drawings/` artwork data**, **`Objects/` reusable assets**, and bundled licensed font resources. Store stable identities and relative links, not absolute machine paths.
- Blank higher authored detail is blank artwork, while grid/entrance/navigation overlays remain usable.
- Object Asset source editing publishes only on **Save**; Save As entered through instance A creates B and rebinds A alone; undo restores A's original link and **keeps B saved**, redo reuses B. Nested Object Assets require acyclic dependencies. Delete offers remove references / NULL placeholders / cancel.
- One Atlas global undo with selection/mode restoration, preserve zoom; camera stays put if any changed geometry is visible, otherwise pans. Recording selection-only steps is an **application-wide opt-in OFF by default**.
- Windows/Linux desktop targets first. Web paused in [[Archive/Web/T-044]]. Historical user-save migration not required.

## Critical engineering contracts remaining
1. **Multi-file storage design and recovery ([[T-066]], [[T-067]]):** choose document manifest encoding, `Drawings/` layout, **larger-than-256 tile geometry based on benchmarks**, signed-chunk index and blob codec, file count/packing/dedup strategy, revisions, staged writes and atomic publication. Validate load-time integrity and backup recovery with files missing/corrupt/out of sync.
2. **Document lifecycle and mapping ([[T-061]]):** stable map/floor/detail-to-document IDs; lazy creation/loading/unloading; visibility of object instances across detail levels; group metadata versus document layer trees; move/copy layer between documents and transaction semantics.
3. **World precision and density:** exact unit conversions and non-lossy signed chunk addressing; per-detail default density progression, edit-target freezing, explicit density change/resampling policy.
4. **Saving and undo across disk:** when an Object Editor Save publishes a new asset version or a map edit commits a new document manifest, define clean/dirty states, local draft history versus global Atlas published history, disk consistency and recovery. Saved retained Variant B must not be deleted on undo.
5. **Nested assets:** when duplicating parent Object Assets, keep child references or deep-clone dependencies? Strong candidate: copy references by default, explicit “make children unique” later; reference cycles must be rejected regardless.
6. **Package/build:** independent Godot project/import layout with exactly one Drawing implementation, safe `res://` paths and class registration.
7. **Owner UX remaining:** supplied Drawing feature inventory under T-059; acceptance of proposed `BarDivider` UI, Asset Browser and source-edit interactions. These should not block a minimal standalone Drawing vertical slice.

## Deliverable / exit criterion
Produce a testable ADR with an **example two-floor/two-detail document registry**, DrawingDocument public API, storage/index layout, create/edit/save/open/undo sequences (including a cross-document layer move and Object Save As), lazy chunk loading and cache budgets, file failure/recovery matrix, and an independent Drawing consumer build. No file format is implied by sample filename extensions.

Allow source extraction and prototype benchmarks where safe; do not imply all implementation is blocked on secondary UI details. **No historical save migration.**

## Round 9 — larger chunk dimension decision
The owner wants **larger chunks than the existing 256×256** to reduce sparse storage overhead and improve compression opportunities. Exact tile size is **not** fixed. Run [[T-067]] comparing 256 baseline with 512/1024/2048 and measure compressed bytes **and** tiny-edit latency, RAM/undo burden, save granularity and sparse inflation. Ensure file packing/sharding is a separate storage decision. Freeze a versioned per-document chunk stride only after the benchmark; no UI choice is required to run it.

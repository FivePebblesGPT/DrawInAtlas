# Give Search and world discovery a clear user purpose

## Source
[[ManualReview_2026-10-30#Usability testing|Usability testing]], item 7.

## Work
Investigate relevant global world-building tools, describe the tasks users expect to solve, and evaluate whether Search, an overview, spatial discovery or another presentation best supports them.

## Acceptance
- Produce concrete user scenarios and sourced reference comparisons.
- Agree feature naming, searchable objects, result context and actions before implementation.
- Demonstrate finding and locating content without requiring knowledge of internal map/link IDs.
- Fit the confirmed shared-board/LOD model rather than assuming the old descendant-document search is the accepted design.

## Investigation evidence — 2026-10-30

See [[SEARCH_AND_WORLD_DISCOVERY]] for four sourced product comparisons,
concrete user scenarios, proposed naming/object/action decisions and the
explicit compatibility boundary with the shared-board and artwork-LOD model.
`tests/research/t009_discovery_probe.gd` is a reproducible **current-state**
witness: it searches for Greyhaven by readable name, focuses the world-board
entrance without requiring internal IDs or changing the edit target, and shows
that campaign-wide document results and unindexed place names do **not** yet
carry searchable board-space location semantics. The probe is deliberately
not a CI gate for preserving the superseded linked-document UX.

**Pending product acceptance:** naming (`Find` / `Find in world`), searchable
place/area objects, result context and `Locate`/`Open details` actions require
explicit owner agreement *before production implementation*. As of this
investigation that agreement has not been provided. The ticket remains open
in [[Index]] rather than calling a research recommendation an accepted feature.

**Local verification:** On Godot `4.8.beta2.official.cafc17a19`, the
research witness passed **10/10** checks, the existing overview suite passed
**67/67**, the organization UI passed **84/84**, and the native framebuffer
reference UI suite passed **46/46** under Xvfb/Mesa. Parser/import and the
explicit-typing guard passed. No application source, schema, UI wording or CI
workflow was changed. Since this is a research/design change, the full
headless/native/export/save sweep was **not** rerun. Remote CI was not run.

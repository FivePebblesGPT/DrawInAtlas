# Explain and clarify raster import/chunk conversion

## Source
[[ManualReview_2026-10-30#Code review|Code review]], item 3: `AtlasRasterLayer.from_image()` has unclear scanning/conversion behavior.

## Acceptance
- Trace its input/output, image normalization, chunk iteration, coordinates, partial edges and memory ownership.
- Determine the actual work performed; do not assume it is a per-pixel scan solely from the review wording.
- Rename, structure and annotate the method so its purpose and cost are apparent from code alone.
- Preserve exact RGBA data, placement and edge chunks; profile only if the investigation finds a concrete performance concern.

## Outcome — 2026-10-30

**Completed:** `AtlasRasterLayer.from_image_chunks()` makes the rectangular chunk-copy contract explicit; `from_image()` remains a compatibility alias. The actual artwork-editor import uses the newly named method. The source now clearly names the rectangle bounds, chunk coordinates, temporary copies and normalization responsibility, with a defensive validity check against partially created imports. No save format, scale/placement policy or chunk dimensions changed.

The mechanism and complexity are traced in [[RASTER_CHUNK_IMPORT]]. Added `tests/raster_import_chunks_smoke.gd` to CI for byte-exact RGBA8, hidden RGB under zero alpha, independent ownership, mipmaps, edge chunks, invalid inputs and native saves. No per-pixel GDScript scan was found; absent a demonstrated performance issue, profiling and redesign were not warranted.

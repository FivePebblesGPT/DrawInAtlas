# Scout PhotoCraft's live-paint pipeline and decide Godot adaptation

**Status: Done (2026-11-06).** Newly scoped corrective work from the owner's first hands-on standalone Drawing review. Source observations are in [the owner review](../DRAWING_USABILITY_REVIEW_2026-11-05.md). Existing earlier "Done" tickets retain their original, narrower acceptance; this ticket does **not** inherit their UX approval.

## Problem / scope
PhotoCraft is a **source-level reference**, not an approved third-party engine or license grant. Establish how a brush becomes visible before release; distinguish input sampling, draft buffers, dirty tiles, compositor, GPU upload, present, and commit. A prior handoff requested this research; track it independently from T-068's large native-kernel experiment.

## Engineering tasks
1. Inspect a **pinned PhotoCraft commit** (include LICENSE and any AGENTS instructions). Trace pointer down/move/up to first visible uncommitted pixel with source permalinks and thread ownership.
2. Trace CPU/GPU rendering, pending-stroke storage, tile dirtiness/caches, zoom/LOD, sampling/interpolation, cancellation, undo and texture publication; do not infer runtime behavior from a README.
3. Compare exact call paths against `addons/drawing/canvas.gd`, `edit_session.gd`, `renderer.gd`, `document.gd`; tag each claim code-proven, measured or inferred.
4. Recommend incremental **GDScript + Godot native graphics** versus selectively benchmarked GDExtension, with end-to-end instrumentation and explicit unknowns.
5. Write `docs/PHOTOCRAFT_RENDERING_RESEARCH.md` with pinned links, execution diagrams, reproducible measurements when runnable, and numbered fixes; use [research handoff](../PHOTOCRAFT_RENDERING_RESEARCH_HANDOFF.md).

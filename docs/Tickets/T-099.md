# Frame-safe Brush input draining and held-preview scheduling

**Parent:** [T-095](T-095.md). **State:** Ready. This ticket has its own independently verifiable outcome; it does not inherit the parent’s remaining manual/device acceptance.

## Problem
A 100-event 96px gesture expanded into 296 segments and drained across 154–166 frames. A staged-only 30ms budget reduced wall time but increased the longest drain call to ~38ms.

## Bounded implementation / research
Reduce scheduling/backlog overhead without hiding samples or blocking held-pointer feedback. Investigate batched event processing, bounded per-frame work, phase scheduling and final-release drain. Keep explicit capturing/draining/committing state and stable source-space gestures across post-release pan/zoom.

## Acceptance and evidence requirements
Use real mouse input and compare 6ms baseline vs candidate p50/p95/max input receipt→preview, queue age/depth, drain calls and release→commit. Require exact full-red source, signed/masked Brush/Eraser, one Undo and post-release navigation; reject any result that trades lower total wall time for unbounded frame stalls.

## Existing evidence / starting point
[Profile and drain-budget negative experiment](../evidence/T-095-2026-11-11-96px-godot-profiler.md).

## Scope boundary
Change only this deliverable; keep canonical straight RGBA8, signed source coordinates, layer/mask semantics and atomic Undo/Redo where relevant. Preserve the existing T-094 fail-closed CI log policy. Record actual commands, exit codes, raw failure controls and source SHA. Do not treat Xvfb/Mesa engine callbacks as physical input-to-photon timing.

# Incremental detached Brush preview compositing

**Parent:** [T-095](T-095.md). **State:** Ready. This ticket has its own independently verifiable outcome; it does not inherit the parent’s remaining manual/device acceptance.

## Problem
In the 96px software witness, repeatedly composing the preview consumes ~4.875s CPU across 161 drain frames. Repainting unchanged preview regions is the largest measured hotspot.

## Bounded implementation / research
Cache/reuse unchanged detached preview tiles and composite only dirty source/display tile regions. Bound cache memory and invalidation by source revision, transform, layer order, selection mask and stroke generation. Preserve the existing 6ms soft drain budget; do not turn a 30ms temporary experiment into a shipping change.

## Acceptance and evidence requirements
A pre-change negative control demonstrates redundant composition. At least two paired cold/warm 96px pointer runs record compositor total/p95, frame count, wall time, peak frame cost and retained bytes. Require exact RGBA8 Brush/Eraser, alpha, signed seams, selection, cancellation, pan/zoom, Undo/Redo and texture/readback parity. No acceptance based solely on a faster isolated renderer call.

## Existing evidence / starting point
[Measured preview hotspot](../evidence/T-095-2026-11-11-96px-godot-profiler.md).

## Scope boundary
Change only this deliverable; keep canonical straight RGBA8, signed source coordinates, layer/mask semantics and atomic Undo/Redo where relevant. Preserve the existing T-094 fail-closed CI log policy. Record actual commands, exit codes, raw failure controls and source SHA. Do not treat Xvfb/Mesa engine callbacks as physical input-to-photon timing.

# Reconnect and resynchronize permitted state

## Source
[[E-008]]: reconnect.

## Acceptance
- Define reconnect identity, revision/snapshot handoff and pending-operation policy.
- Restore consistent permitted state after missed edits without duplicating accepted operations.
- Filter resynchronization payloads by current permissions, including revoked visibility.
- Test interrupted sessions and stale clients with no silent data corruption.

## Engineering checkpoint (2026-11-01)

Implemented trusted-handle disconnect/reconnect in the isolated T-045/T-046
host/client proof. A disconnected client cannot issue commands or resync, and
its viewer artwork is immediately cleared. A trusted controller can resume
only the exact previously registered handle, receiving a new handle and a
current host revision/full snapshot **filtered by current permissions**.
Offline grants/revocations do not replay stale pixels. The per-peer request
ledger and sequence survive reconnect, allowing explicit retry of an uncertain
last command without duplicating accepted edits. No pending operation is
submitted automatically; original handles remain retired. Host divergence,
history undo and session closure deny resumption.

Test suite: `tests/reconnect_resync_smoke.gd`, CI coverage, and
[[RECONNECT_RESYNCHRONIZATION]] protocol notes. **Acceptance still open:**
secure authenticated transport, process-restart recovery/journaling,
real-world disconnect and timeout testing, production integration, owner
agreement on pending-operation semantics, and independent privacy review.

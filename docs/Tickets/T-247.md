# Reserve Atlas history during synchronous changed notifications

**Bounded T-148 child.** T-245/T-246 reserve host history during Drawing
publication and ordinary command application. However `changed` notifications
from `undo`, `redo`, selection history, `reset`, `mark_saved`, and
`mark_external_change` were emitted without a timeline reservation. Synchronous
observers could immediately start nested commands, consume a redo branch,
reset history or overwrite save/dirty checkpoints before the outer notification
returned.

## Acceptance

- [x] Reserve every synchronous `changed` emission across all Atlas history
  entry points; observers may read completed state, but cannot mutate the
  history through public entry points during that notification.
- [x] Preserve one notification for each outer operation, chronological
  Undo/Redo, selection-only history, save/external dirty semantics, and reset.
- [x] Release the reservation after the notification, preserving ordinary
  subsequent commands and replay.
- [x] Reproduce the issue against the previous code, add an exact-count native
  Atlas regression to required fast CI, and run neighboring history/transfer
  integration suites.

## Completion — 2026-11-22

The 259-check Atlas regression fails **124/259** checks on the preceding
implementation and passes **259/259** after introducing one shared notification
reservation. The nine selected neighboring standalone/Atlas suites pass, including
T-245/T-246, global history, native history, replay, ownership and transfer.
The native-X11 Canvas 46-check regression also passes without per-pixel
tile-stream FFI calls.
See [execution evidence](../evidence/T-247-2026-11-22-atlas-notifications.md).

**Scope:** Synchronous `AtlasEditHistory.changed` observers. It does not guard
arbitrary direct model mutations, make all raster paths natively authoritative,
or establish hosted CI or owner-hardware approval. T-148 remains In Progress;
T-149 remains Blocked.

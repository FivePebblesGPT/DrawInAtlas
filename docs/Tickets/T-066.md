# Persist sparse per-floor/detail DrawingDocuments as multiple files

**Status: PLANNED.** Owner confirmed **Option B** plus sparse, multi-file storage (2026-11-02). No old user saves need conversion.

## Scope and contracts
- Atlas owns one stable, generic `DrawingDocument` per `(map_id, floor_id, detail_id)`. A logical empty detail may have a document ID but no chunk files until it is first painted.
- The campaign root records metadata, authoritative map/floor/detail -> document IDs, world resolution, layer/group references and navigation. It must not eagerly embed every Drawing pixel into a `.scn`.
- A sibling `Drawings/` tree stores document manifests and **only nonempty sparse canonical raster chunk payloads**. A sibling `Objects/` stores independently reusable, savable Object Assets; font resources also travel with the project.
- Current source code already has **256×256 as its baseline, not the target size**, signed chunks and SHA-256 content IDs (`AtlasRasterChunk`), `AtlasRasterLayer` maps and exact WebP codec checks (`AtlasWebPStore`). **Owner prefers larger chunks.** Reuse validation concepts but select the new logical chunk size via [[T-067]] and version it in the document format. The present `AtlasCampaignStore` still does not write separate chunk files.
- Drawing's file IO/public document API is generic, without importing Atlas map/floor/LOD types. Atlas's storage coordinator resolves docs and project-relative paths.

## Suggested architecture to investigate (not a preapproved file schema)
```text
Campaign.scn            # stable map/floor/detail -> document registry and metadata
Drawings/
  documents/<doc-id>.*   # layer tree, chunk refs, chunk coords, pixels-per-unit
  chunks/<prefix>/<digest>.webp    # deduplicated, lossless, content-verified chunk data
Objects/<asset-id>.*     # reusable asset sources and optional data references
Fonts/...                # legally bundled required font files
```
**Do not freeze one file per chunk or chunk size 256.** Candidate logical sizes 512/1024/2048 (256 baseline) must be measured under [[T-067]]. Independently benchmark one-file-per-chunk, per-document pack and shared content-addressed pack/index to reduce filesystem overhead. Content addressing is a candidate, not a mandate.

## Implementation plan
1. Define durable **document ID** mapping per Atlas floor/detail, separate from user-facing tab identity and layer IDs. Preserve global map/world coordinates across documents, per-detail density and per-layer transforms.
2. Extract one generic DrawingDocument codec and an on-demand `ChunkStore` interface. Reuse validated RGBA8, signed index, SHA-256 and lossless WebP code; choose final file schema, digest and manifest versioning explicitly. Support sparse empty layers and absent chunks.
3. Build a project-relative `Drawings/` storage coordinator and manifest index. Write changed chunks only; avoid serializing unrelated map/detail documents or allocating blank images. Verify manifest references before publishing.
4. **Crash-safe cross-file save:** stage and verify new chunk blobs/manifests, then atomically update a single authoritative generation/root pointer (or a documented equally safe transaction scheme). Never leave a valid root pointing at missing content after interrupted writes. Preserve prior good generation for recovery; non-atomic assumptions about renaming several files are forbidden.
5. Load only active/visible detail documents and viewport chunk ranges; use LRU caches, explicit invalidation, bounded memory/file handles and asynchronous work only where safe for Godot. No silent data loss when dirty documents unload.
6. Integrate Atlas global undo for edits across two distinct DrawingDocuments and independent Object Assets. Pin undo-referenced generations/chunks until safe cleanup. **Garbage collection must never delete retained B or live/saved/undo-referenced blobs.**
7. Test portable move/rename, incomplete project copy, missing/corrupt/mismatched chunk, byte-exact alpha including transparent RGB, negative chunk coordinates, partial chunks, large sparse boards, write failures, crash timing, concurrent active documents, rename, selection/masks and object references.
8. Benchmark one small edit on a huge map: serialization scope, filesystem calls, save latency, load latency, CPU/RAM/VRAM and file-count scalability vs baseline. Record a documented strategy for compaction or “Optimize project” rather than unsafe automatic cleanup.

## Acceptance
Each floor/detail has **one stable internal DrawingDocument**; only changed, populated chunks and necessary metadata persist across distinct files; the campaign plus sibling `Drawings/`, `Objects/` and licensed fonts is portable; save/reload and failure recovery are coherent, exact-pixel, sparse and nondestructive. Empty detail stays blank but overlays work. Two-project Drawing/Atlas independence remains intact; no Web build or old-save migration gate.

## Open technical options
Chunk format and naming, content-dedup scope, one-file-per-chunk versus shard/pack, generation commit implementation, retention/compaction, object-asset chunk storage sharing, update-savepoint semantics. Resolve by an ADR + measurements, not guesswork.

## Round 9 — larger chunks, storage geometry and benchmarks
The owner challenged the inherited 256×256 geometry because many small sparse files add metadata cost and can reduce WebP's compression efficiency. **Resolve the new chunk dimension with [[T-067]] before freezing on-disk chunk coordinates/schema.** Leading **hypothesis** is 1024×1024, not a locked requirement. Benchmark 256/512/1024/2048, and treat **logical chunk size** and **physical files per chunk** as separate variables.

The storage manifest must encode a **stable, versioned tile-size invariant** (normally per document); signed chunk `(cx,cy)` implies a pixel origin based on that declared size. Prevent a chunk created using one dimension from being reopened with a different assumed stride. Any later retiling is an explicit new-format operation.

Measure compressed size, metadata and file count, tiny-change re-encoding, latency to publish, load and cache churn, peak decoded memory, undo/delta size and sparse isolated-mark inflation. Keep no files for never-authored regions; use lazy chunks even for large tiles. A fixed one-file-per-tile policy is not automatically the most space-efficient multi-file layout.

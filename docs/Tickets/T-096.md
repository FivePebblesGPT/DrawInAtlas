# Accurate large selection contours and low-latency floating Move

**State: Manual Review (2026-11-07).** Contour and Move engineering plus independent model/Xvfb native tests are complete. The **owner's physical interactive UX acceptance remains unapproved**; no synthetic pointer or Mesa software-renderer result closes it.

## User reproduction

Create a painted region spanning multiple storage/display chunks. Select a meaningful rectangle or a mask with Add/Subtract islands and holes. The initial marquee disappears and a larger, less precise outline appears; moving the selected pixels is **visibly laggy**. Selection and Move should not look like a box around all nonempty pixels, and the user must be able to distinguish the selection boundary from a conservative bounding rectangle.

## Confirmed pre-fix code behavior / hypotheses

Before the implementation documented below, in `addons/drawing/canvas.gd`, `_draw_selection_outline()` traces the actual mask only when `selected.size.x * selected.size.y <= 4096` and zoom >= 0.5. Larger masks deliberately draw the enclosing rectangle and operation guides. This explains why an initially precise outline can become a larger box; it is not evidence that the actual selection *data* became rectangular.

Before this fix, a floating Move called `_stage_move_preview()` as the pointer displacement changes. It started a new edit session and called `DrawingClipboard.move_selection()`, which captured source pixels, cleared the selected area and pasted at each new displacement. The measured cost and updated implementation are recorded below.

## Engineering tasks

1. Separate the transient drag marquee, persistent mask boundary, enclosing bounds and floating-content footprint visually and semantically. Avoid claiming that a bounding rectangle represents the exact selection.
2. Render visible selection contours with bounded work at large sizes: cache mask boundaries/tile spans or recompute only viewport-visible edges; preserve disjoint islands, holes and subtract/intersect semantics.
3. Profile Move pointer-event latency, source capture, clear/paste, session construction and compositor invalidation. Avoid recapturing the identical original source on each drag update; reuse immutable source/mask data and update only affected preview regions.
4. Preserve cumulative floating Move, repeated drags before explicit drop, Escape cancellation, click-outside behavior, correct layer depth, signed chunk boundaries and one Undo/Redo content transaction.
5. Add native pointer/framebuffer tests for selections exceeding 4096 pixels, complex masks, rapid drags at multiple zooms, and cold/warm viewport performance.

## Acceptance

- [x] Large selections display visible islands/holes with viewport-bounded rectangle tracing and budgeted cached explicit-mask tiles; panning/zoom tests pass in software. **Physical GPU performance remains unmeasured.**

## 2026-11-07 implementation and software-only validation

**Contours:** Replaced the 4096-pixel fallback enclosing rectangle with exact viewport-clipped persistent mask boundaries. A scanline interval evaluator applies the ordered rectangle-expression operations (including holes and islands) in O(visible rows × mask operations), not O(selected area). Explicit per-pixel masks are traced progressively in 64px source tiles, capped at four new tiles per frame and a 4096-tile cache; no speculative filled bounds are drawn. A source-coordinate edge oracle verifies all displayed segments against independent pixel-neighbor truth including signed tile seams and extreme enclosing extents. The marquee remains the yellow transient guide; blue edges are real persistent mask boundaries.

**Move:** A first pointer-down captures the immutable source once for the entire floating transaction; each offset stages sparse selected nonzero RGBA8 pixels without repeated source capture or full-rectangle clear/paste. Captures include alpha-zero/nonzero RGB, never sample floating drafts, and are dropped on confirmation/cancel/no-motion. Ordinary pre-staged public `move_selection` maintains full-rectangle semantics. Updated per-phase instrumentation covers capture, new-session construction, staged edit, selection translation, input-receipt-to-preview submit, contour drawing and actual drop CPU; these are **not** physical input-to-photon readings.

**Evidence:** [T-096 paired legacy/new CPU profile and native framebuffer measurements](../evidence/T-096-2026-11-07-selection.md). Eight byte-identical same-offset old/new comparisons: old `capture` p50/p95 **15.046/15.334ms**, `clear_rect` **41.896/43.166ms**, `paste` **13.530/14.196ms**; new stage against one retained capture **15.388/16.277ms**. Xvfb/Mesa root-delivered pointer Move: staging/selection preview-submit **9.324/11.057ms** and input receipt-to-submit **9.463/12.093ms** p50/p95; pointer-to-postdraw callback **40.345/47.638ms**; outside-click drop **7.996ms CPU** and **43.104ms** through two test frame callbacks. The source-/framebuffer oracles, 25%/400%/786% native drags, holes/islands and layer/Undo/Redo regressions all pass. A separate on-demand `godot-native-t096-selection.yml` workflow stages canonical source and runs the witnesses without claiming owner hardware validation; it has **not** been run on hosted CI here.

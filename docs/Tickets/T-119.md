# Reject GM Token edits after campaign/map/floor registry replacement

**Independent outcome:** Done for this narrow token-source authorization fix.
T-041 remains **Blocked** on T-039's explicit player-privacy policy and
owner-facing token interaction/visibility decisions. This ticket neither
publishes tokens to players nor approves those policies.

## Problem

The Token drag guard already froze the map, floor, token-layer Resource, full
token content, and edit mask, but only compared those pointers to the Canvas's
retained pointers. If an identical-ID map or floor was replaced or removed from
the live campaign registry, the drag could still emit `token_edit_requested`.
The ID-addressed Editor command could then change a replacement token layer
and append an Undo entry. Immediate placement, delete and direct Editor token
commands had the same detached-resource authorization gap.

## Fix

- Capture the original campaign Resource at Token mouse-down, require it still
  owns the exact registered map/floor at every update and release, and clear
  the captured campaign when the drag ends or is rejected.
- Reject stale previews before dispatch; clear preview/selection and retain
  the existing `token_rejected` guidance.
- Deny token creation/deletion from an unregistered Canvas target and make
  `_edit_token()` verify the Canvas and Editor share the same live campaign
  and registered map/floor before issuing an ID-addressed history command.
- Preserve exact token IDs/content, masks, source revisions, signed positions,
  valid unrelated-map changes, and single-step Undo/Redo. No saved schema,
  player-output policy, Rust ABI or renderer change.

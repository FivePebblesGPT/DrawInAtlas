# Re-profile the current Drawing app's frame drops and native stroke path

## Owner testing — 2026-11-17, after PR #20

The owner says drawing now seems usable, but instead of the former visible
delay the frame rate appears to drop to roughly **12 FPS**. This is a subjective
estimate, not an instrumented frame-rate result or final physical acceptance.
The owner requests fresh profiling and suggests **250ms**, preferably **200ms**,
as a comfortable near-term target for halving the previously discussed ~0.53s
workload. The duration metric must be stated; FPS and gesture latency differ.

## Deliverable

1. Profile the **current full Drawing workspace now**, after the T-181 visible
   tile fix. This is a current-snapshot investigation; the later fully
   consolidated T-151 gate remains separate and blocked by T-150.
2. Record repository/native/preset hashes, tool versions, hardware/rendering
   mode, image/layers, zoom, width, opacity, input path and delivery cadence.
   Exercise real moving and stationary-held input at the owner's ~54% view,
   plus 100% and the existing 96px/512² serpentine benchmark. Include erase,
   overlap, cold/warm caches and repeated strokes.
3. Capture frame intervals/FPS distribution and long frames, first-preview
   delay, input age/backlog, release→commit and release→settled-display latency.
   Report the existing T-146 `total_to_postdraw_ms` separately so the 250/200ms
   proposal can be compared with a reproducible declared workload/statistic.
4. Attribute time and copies across input/queue, native rasterization and tile
   staging, GDExtension transfers, preview invalidation/compositing, texture
   update/upload, draw and post-draw callbacks, and commit/history. Use Godot
   function profiling and native sampling where available; avoid double-counting
   nested inclusive durations as disjoint wall time.
5. Rank the measured bottlenecks and propose one falsifiable first change for
   T-186. A lead, not a conclusion: cumulative native dirty descriptors currently
   make `_stage_native_tile_batch()` advance old tile stamps, while the correct
   T-181 fix refreshes warm textures rather than hiding them behind cold budgets.

## Acceptance

- [ ] Reproduce or bound the reported frame drop with actual frame-time data,
      repeated cold/warm runs, median/p95 and raw incomplete/failing runs.
- [ ] Pin a fresh baseline and target metric; explain how ~12 FPS, ~83ms frames
      and a ~529ms scripted burst can coexist without treating them as equal.
- [ ] Rank frame-stall/critical-path stages with measured function/copy costs;
      identify a bounded optimization and a counterfactual that could reject it.
- [ ] Preserve T-181's visible-framebuffer regression and native source,
      history, masks and persistence checks while profiling.

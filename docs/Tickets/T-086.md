# Incremental viewport compositing, cached textures and zoom scaling

**Status: In Progress (2026-11-06).** Source-space cached display tiles and software tests implemented; owner physical-hardware acceptance and first-population/large dense viewport optimizations remain. Newly scoped corrective work from the owner's first hands-on standalone Drawing review. Source observations are in [the owner review](../DRAWING_USABILITY_REVIEW_2026-11-05.md). Existing earlier "Done" tickets retain their original, narrower acceptance; this ticket does **not** inherit their UX approval.

## Problem / scope
Standalone `DrawingCanvas._draw()` currently re-renders the visible document in 192px CPU rectangles and calls `ImageTexture.create_from_image()` on each redraw. Zooming out exposes many more source pixels and makes the app lag even for small edits. T-068's small CPU benchmark does not prove full-viewport responsiveness.

## Engineering tasks
1. Profile `DrawingRenderer.render`, memory allocations, texture creation/upload, frame submission and visible-tile count by zoom/layer count.
2. Maintain persistent display texture tiles keyed by document/layer/composite revision and view transform; schedule only dirty tiles/rectangles, with bounded cache and eviction.
3. Separate storage stride, edit dirty area and GPU display tile geometry. Use Godot native textured quads and GPU scaling; investigate derived LOD/mipmaps on zoom-out without changing canonical pixels.
4. Update textures when necessary rather than creating images/textures on every pointer redraw. Do not assume `ImageTexture.update()` is partial-rectangle upload.
5. Ensure pan/zoom/visibility/selection/asset publication/undo trigger correct invalidations; preserve transparent pixels and signed seam geometry.

## Acceptance / verification
- [x] Small raster edits invalidate nearby display content rather than the full view (headless dirty-journal and software framebuffer witnesses, one existing 128px tile per 1px edit/Undo/Redo).
- [ ] Pan/zoom and 25%/50%/100% with multiple layers do not stall UI input or exceed documented bounded cache memory **on reference Windows/Linux hardware and large dense documents**; software cached redraws are fast but first 50% population regressed in one run.
- [x] Byte/pixel parity across signed tile seams, layered alpha, text, visibility, cancellation and history (Godot native Xvfb/Mesa readback; physical display still pending).
- [x] Reproducible before/after CPU-composite, texture-call and software-frame median/p95, process HWM, exact workload, Godot version and llvmpipe context; physical GPU/display measurements still pending.

## T-084 evidence checkpoint — 2026-11-06

The [PhotoCraft source research](../PHOTOCRAFT_RENDERING_RESEARCH.md) confirms persistent GPU-resident 256px layer tiles, dirty composition, persistent display textures and partial/mip updates. In Godot `ImageTexture.update()` replaces a *whole display texture*, so adapt the principle through independent 128–256px **display** tiles and dirty-only updates, without claiming arbitrary subrectangle updates. Storage tiles, brush-coverage tiles and display tiles have distinct roles. Camera-only pan/zoom should reuse cached content. Note the standalone canvas currently clamps zoom to 50% minimum: explicitly widen the benchmark transform before promising 25% UI tests. T-084's no-runtime source study is not evidence of speedup; measure real standalone CPU render/upload/frame timings.

## 2026-11-06 implementation checkpoint — source-space persistent display tiles

**State: In Progress; implementation and software witnesses pass, not owner/hardware accepted.**
Canonical `addons/drawing/` now maintains a source-aligned **128×128 display-tile**
LRU cache, independent of 256px default storage tiles and the brush coverage
mask. At most **144 retained textures** (9,437,184 straight RGBA8 payload
bytes) are cached. The viewport draws Godot texture quads with the current
zoom transform; camera-only movement and zoom do not change texture keys. The mouse-wheel
and workspace zoom floor now allow **25%** instead of the older 50% clamp.
`ImageTexture.update()` always uploads the **entire 128px display texture**, so
one dirty tile is a **65,536-byte full-texture upload**, not a fictitious
subrect update. Disjoint sparse tiles are skipped before rendering rather than
allocating empty textures; the occupancy index is capped at 40,000 entries
and falls back to conservative rendering if exceeded.

`DrawingDocument.display_changes_since(revision)` is a separate 64-entry
monotonic content-publish journal; it is deliberately independent of the
persistence `_dirty_tiles` savepoint set. A plain raster edit, Undo or Redo
invalidates cached display tiles only where published `DrawingDirtyRegion`
bounds intersect. Missing revisions from structural, visibility or text edits,
loader registration changes, document swaps and journal eviction trigger
conservative invalidation. Visibility, text glyph bounds and sparse source
footprints are represented in the occupancy index; content edits extend
that index incrementally (erased footprints can temporarily remain occupied,
which is safe but may cause extra transparent work). Detached stroke previews
carry per-storage-tile generations and are compared per display footprint;
changed preview tiles recompose in layer order without invalidating unrelated
textures. Cancellation and commit reconcile against the canonical document
without ghosting or changing history semantics. For very small storage strides,
preview version lookups scan the sparse changed-key set rather than a huge
negative/positive tile grid.

### Software-only measured comparison

Debian 13, Godot `4.8.beta2.official.cafc17a19`, X11 Xvfb/OpenGL
Compatibility, Mesa 25.0.7 llvmpipe (LLVM 19.1.7), window **640×460**, Control
**212×164**, software renderer (no real monitor/DPI, physical GPU, Windows or
hardware input). Each run has two layered 64×64 RGBA sources and **12** warmed
forced redraws per zoom (idle) plus **12** separate one-pixel commits and redraws
(edits), at **100%, 50%, 25%**. The baseline uses original T-085 `canvas.gd`
from the SHA-256-validated archived T-085 pre-cache source fixture (taken
from `5f4e3a3`), instrumented with observational CPU timing probes, staged into
a separate standalone app; the current cache uses its production metrics.
The comparison script builds/imports both isolated apps and measures
CPU-composition, synchronous texture-call time, pixels recomposed, complete
texture byte uploads, and redraw-to-`frame_post_draw` wall time. No GPU
physical transfer completion or input-to-photon is inferred. Median/p95 below
are milliseconds unless noted.

| Zoom | Idle frame old → cached p50 / p95 | One-pixel edit frame old → cached p50 / p95 | Edit CPU compose old → cached p50 / p95 | Edit full-texture upload old → cached |
| --- | --- | --- | --- | --- |
| 100% | 44.73/45.65 → **1.36/1.50** | 44.78/52.91 → **23.31/24.76** | 42.56/49.94 → **20.45/22.17** | 142,096 → 65,536 bytes |
| 50% | 129.85/206.00 → **2.14/5.09** | 131.27/147.15 → **26.82/30.77** | 128.43/143.25 → **23.17/26.28** | 562,320 → 65,536 bytes |
| 25% | 262.93/276.10 → **1.50/1.76** | 253.09/278.94 → **22.96/27.55** | 248.80/274.52 → **20.34/24.15** | 2,237,200 → 65,536 bytes |

In the same comparison, idle CPU compose/texture-call time drops to zero on
all zooms after warmup. Cached one-pixel updates render exactly 16,384 source
pixels and update one existing texture; the baseline rendered 35,524 /
140,580 / 559,300 source pixels at the three zoom levels, creating fresh
textures each redraw. The 50% **zoom transition** took 144.22ms baseline
versus **165.52ms cached** while newly exposed tiles were populated; this is
a genuine regression in that single cold-transition sample, not evidence of
smooth first-time full-canvas drawing. The 25% transition was 257.80ms old
versus 2.14ms cached because prior 50% had already warmed all content tiles.
Zoom transitions were **one sample each**, not p95 estimates.

A separate repeat run on the same software stack produced warmed **25%**
small-edit frame **237.46ms → 23.01ms** median and idle frame
**239.19ms → 1.54ms** median. The **50% cold transition** again regressed:
**124.16ms → 163.85ms** (single sample). The fixture is checked into
`tools/benchmarks/fixtures/` with a pinned digest so applying or squashing
this mailbox cannot silently break the before/after workflow by changing the
historical commit hash.

The Linux process `VmHWM` measured **240,284 KiB baseline** versus
**241,640 KiB cached** in separate fresh Godot processes; their allocator
tracked peak was 65,132 KiB each. The 9MiB bound covers **retained RGBA8
texture payload estimates**, not actual video RAM, internal engine allocations
or in-flight draw-command references (which remain alive until the next draw
to prevent use-after-free/flicker when the view exceeds the LRU capacity). The 1,000×680 source-space stress at 25%
showed 704 potential display tiles, **688 skipped as empty**, 16 retained.
When occupancy cannot safely be indexed, a separate **192-visible-tile**
conservative software fallback retains **144** cache entries and renders
**48** transient tiles on a repeat redraw (**144 hits**, 48 texture creations;
12,582,912 bytes of simultaneous draw-command texture payload estimates).
This corrects the former all-tiles-per-frame LRU churn. The **9 MiB** budget
applies only to persistent entries; an oversized *current* frame can hold more
transient texture references. This is an explicit remaining memory/performance
limitation, not a hardware VRAM bound. `frame_post_draw` is a submission
milestone, **not physical scan-out**.

## 2026-11-06 cold-composite optimization checkpoint (still In Progress)

Optimized only the canonical `DrawingRenderer._composite_raster` hot path. A
single bounded render now reuses up to 256 resolved storage chunks and their **detached** preview
patches per storage-row band (instead of per scanline), and
writes fully opaque source RGBA8 directly without evaluating straight-alpha
source-over or reading the obscured destination. Source alpha 0 still leaves
previous destination bytes untouched; fractional alpha still uses the original
`DrawingEditSession._blend`. Failed lazy resolution still returns the original
error; no missing/corrupt chunk is converted to a transparent success.

The temporary lookup is **not** a new persistent cache: it resets at each
storage-tile row, retains at most 256 references per band and does not retain
1px-stride tiles (which never repeat across rows). This prevents a 1-pixel
storage stride or an exceptionally wide bounded view from allocating an
unbounded one-reference-per-pixel dictionary. Canonical storage, dirty journal,
display texture limits, preview publication and persisted pixels are unchanged.

## 2026-11-06 direct indexed raster read checkpoint (still In Progress)

**Scope:** Further optimized the same bounded CPU `DrawingRenderer._composite_raster`
loop. For each resolved source-tile run the renderer now holds a read-only
reference to the tile's canonical sparse `Dictionary[int, int]` map and indexes
pixels by their existing linear storage indices, instead of calling
`DrawingRasterTile.get_rgba(x, y)` (including coordinate assertions) per
pixel. The read path does **not** mutate the map, retain references beyond the
synchronous render, bypass lazy source/digest validation, or write preview
pixels into committed tiles. Empty detached-preview patches skip per-pixel
`has()` queries; nonempty patches still override precisely their touched
pixels, including erasure and zero-alpha hidden RGB.

**New exact parity checks:** The extended
`drawing/tests/renderer_cold_tile_smoke.gd` passes **45/45** assertions,
including four densely populated layers crossing signed 8px storage seams,
all five alpha categories, byte-exact comparison against a deliberately slow
public-read oracle, unchanged canonical tile bytes/revision, and detached
lower-layer preview plus cancellation. The existing T-086 68/68 Xvfb/Mesa
framebuffer test passes after staging **and** importing the standalone
package (bundled font import is a prerequisite). The `test_t086_benchmark_fixtures.py`
fast-CI contracts verify both historical renderer SHA-256 pins, source drift
and rejection of altered comparison fixtures. This does not add a new CI step

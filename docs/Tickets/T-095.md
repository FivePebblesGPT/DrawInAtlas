# Profile and eliminate severe 60px Brush latency

## Latest owner testing — 2026-11-17, after merged PR #20

The owner reports that Drawing **seems usable**, but now appears to drop to
roughly **12 FPS during drawing** rather than showing the former delay. This
is an owner estimate, not an instrumented profile or explicit final acceptance.
They request profiling again and suggest approximately halving the discussed
~0.53s workload to **250ms**, preferably **200ms**, for comfortable drawing.

[T-185](T-185.md) profiles the current snapshot now, independently of T-151's
later post-consolidation gate; [T-186](T-186.md) and [T-187](T-187.md)
implement measured current optimizations. The unchanged rapid 100-event 96px
p50 after T-187 remains **343ms cold / 344ms warm**, above both the 250ms
milestone and 200ms stretch. [T-189](T-189.md) owns that remaining gap after T-188's measured native staging step;
this is not physical owner acceptance. Record frame-time/FPS, first preview, input backlog,
release→commit and total benchmark latency separately. Treat 250ms as the
current-sprint practical milestone and 200ms as the stretch target, with the
metric and statistic declared. The older 100ms aspiration below is historical
context for the longer-term pipeline, not a reason to change these new targets
silently. This parent remains In Progress with its physical owner gate open.

## User reproduction

On a new approximately 512×512 Drawing image, zoom to about **786%**, choose a **60px Brush**, and attempt to cover the visible canvas without a bucket/fill tool. The owner reported a roughly **three-second pointer stroke taking approximately one minute to render**. Subsequent Undo/Redo is much faster. This must be reproduced through the **actual Brush tool and pointer events**; direct `DrawingEditSession.fill_rect()` is not representative.

The 2026-11-07 Godot 4.8 beta 2 software-renderer diagnostics did *not* reproduce the minute-long UI stall: two 60px mouse strokes covered the displayed area with ~0.47s release-to-commit per stroke in that setup. An isolated nine-sweep, 259,290-pixel `paint_path` benchmark measured ~3.04s staging plus ~1.19s commit on one software-run sample. Neither constitutes a physical GPU/pointer acceptance result or disproves the owner's report.

2. Attribute wall time by **input receipt → queue → staging → detached preview compositor → texture allocation/upload → frame draw/post-draw → release/commit**. Record per-phase p50/p95 with repeated strokes and distinguish physical input-to-photon latency from Godot frame callbacks.
3. After T-150, profile Rust rasterization, native tile staging/commit/Undo, GDExtension batch/dirty-tile copies, Godot texture upload and frame callbacks (T-151). Optimize the measured dominant new hotspot in T-152, not a retired GDScript `_stage()` loop.
4. Preserve **per-mode** defined brush coverage/pigment semantics, straight-RGBA8 and hidden-RGB source correctness, signed chunk boundaries, selection masking, layer compositing, cancellation and one Undo/Redo step per stroke. Hokusai hard-round is not required to reproduce Legacy hard-brush pixels.
5. Add a native interactive 60px benchmark/regression at 786% plus a headless byte-exact independent stroke oracle. Record cold and warm cases; test hardware separately from Xvfb/Mesa.
